* OPEN — nostrdown prefix matching is case-sensitive, clashing with the spec's ABNF
:PROPERTIES:
:found: 2026-08-10 (spec-conformance audit of the nostrdown tokenizer)
:END:

** Symptom
={{Ref:intro}}= / ={{WIKI:topic}}= parse as literal text — the tokenizer
(=RefKind::from_prefix=, =src/nostrdown.rs=) matches prefixes exact-lowercase
only. The spec's ABNF (=docs/nostrdown-spec.md=, =prefix = "ref" / …=) uses
string literals, which are case-insensitive by RFC 5234 convention, so a
conforming author could write ={{Ref:…}}= and get prose instead of a link.

** Fix direction
Lowercase the prefix before the =from_prefix= match (one =to_ascii_lowercase()=
on the prefix slice; same for the =[[ ]]= path if ever applicable). The spec's
parsing rules note the current case-sensitive behavior until this lands.

* OPEN — flaky test: =test_get_addressable_returns_latest_version= under parallel runs
:PROPERTIES:
:found: 2026-07-09 (during client-tag provenance work; reproduced on HEAD without the change)
:END:

** Symptom
=cargo test --lib= intermittently fails =engine::tests::
test_get_addressable_returns_latest_version= (~1 in 3 full-suite runs);
always passes in isolation. Pre-existing — reproduced on a clean tree.

** Suspected why
The test ingests two versions of the same =30023= coordinate via
=ingest_and_wait= and expects latest-wins. Under parallel test load the
wait (nostrdb subscription) likely returns before *both* events are
indexed, so =get_addressable= sees only the older version. Fix direction:
make =ingest_and_wait= wait for the expected note count (or ingest + wait
per event) instead of a single subscription poll.

* FIXED — system prompt not shown until the first chat message
:PROPERTIES:
:found: 2026-06-08 (during AI tool-calling feature work)
:fixed-in: feat(web): AI agent chat … (folded into the feature it belongs to)
:END:

** Symptom
The chat's *System* view was empty on load. The system prompt (read from
=prompt.md=) only appeared after the user sent a message — even though the
engine had it the whole time. Expected: present as soon as the chat opens.

** Why
The system prompt is hydrated into =app.chat= by =getChat()=. On load that
only ran in =initialize()= (=+layout= onMount), which could race the engine
and, once stale, never re-fetched — HMR / component updates don't re-run
=initialize()=. The chat panel mounts lazily (a wm buffer), so by the time it
opened, =app.chat.system_prompt= was the stale =null= from the first load. A
message *did* refresh it because =handleAgentStream= reconciles with
=getChat()= after each turn. Compounding it: =SystemPrompt.svelte= captured
=currentPrompt= once via =$state(currentPrompt ?? '')= (Svelte 5 — not
reactive to later prop changes), and =chat_reset= wiped the prompt entirely.

** Fix
- Engine: =chat_get=, =chat_reset=, and each agent turn re-read =prompt.md=
  into =chat.system_prompt= (=src/api.rs=), so =GET /chat= always reflects the
  file (survives reset + on-disk edits).
- Web: =ChatBuffer= calls =app.refreshChat()= (→ =getChat()=) on mount, so the
  panel hydrates whenever it opens — not only after the first message.
- =SystemPrompt.svelte= resyncs its buffer when =currentPrompt= changes (a
  guarded =$effect=), without clobbering an in-progress edit.
- =POST /chat/system= and =PUT /ai/prompt= both write =prompt.md=, keeping the
  chat System view and the AI-settings prompt editor in sync.

* FIXED — /publish/blocks produced unsigned events for NIP-07 users
:PROPERTIES:
:found: 2026-05-30 (during the boundary-compliance cleanup)
:branch: bugs/publish-blocks-signing
:END:

** Symptom
A user logged in via NIP-07 (browser extension) who publishes a publication
that contains *any* imported or forked section — or whose draft was seeded
from a publication in the reader — emits events with an all-zeros placeholder
signature (=\"0\".repeat(128)=). Relays reject them as invalid.

** Why it bit NIP-07 specifically, and why it's the common path
- =web/src/lib/state.svelte.ts= routes a compose publish to =/publish/blocks=
  (vs =/publish=) whenever =hasProvenance= is true: =composeSourcePubAddr= set
  (draft seeded from a publication) OR any section carries =source_addr= (added
  to compose from the reference pool). The "→ compose" pill is wired across
  feed / search / reader / profile surfaces, so for this reference-centric app
  the block path is the *default*, not an edge case.
- =publish_blocks_handler= (=src/api.rs=) did NOT take the =SigningController=.
  When =sign= was requested it ran an inlined legacy secret chain — session
  secret → keyring =get_secret= → =.env= ncryptsec decrypt — all of which only
  find a secret key sitting *on the engine host*. A NIP-07 user has no such
  secret (the key lives in the extension; signing happens in the browser over
  the SSE back-channel), so the chain fell through to =None=.
- =build_block_publication_events(.., None)= then signs each event with the
  placeholder =\"0\".repeat(128)= sentinel (=build_section_event_internal= /
  =build_forked_section_event= / =build_block_index_event=). Unsigned events
  get built and broadcast.
- Meanwhile =/publish= (=publish_handler=) already signs through the
  =SigningController=, which abstracts the key source (engine in-process /
  NIP-07 / NIP-46). So the two publish surfaces had divergent identity
  semantics: the same logged-in user could publish via =/publish= but not
  =/publish/blocks=.

** Fix
Route =publish_blocks_handler= through the =SigningController= exactly like
=publish_handler=:
- Add =Extension(signing): Extension<SigningController>= to the handler.
- New =publication::build_signed_block_publication_events_via_signer= — builds
  the full block graph *unsigned* via =build_block_publication_events(.., None)=
  (reusing the canonical fork/import tag + coordinate logic), then re-signs
  every event through the =Signer= using the existing
  =resign_value_through_signer= helper. Re-signing is reference-safe because
  =a= tags address sections by =kind:pubkey:d_tag= coordinate, not by id/timestamp.
- Delete the inline session/keyring/.env secret chain.
- Regression test =signer_routed_block_publish_is_actually_signed=: asserts no
  event carries the placeholder sig (exercised with =InProcessSigner=; the
  NIP-07/46 =ExternalSigner= satisfies the same =Signer= trait).

Independent of engine in-process signing being implemented/tested — the fix
only needs the =SigningController= path that =/publish= already uses.

** Verify
=cargo test= (incl. =signer_routed_block_publish_is_actually_signed=);
=cargo clippy= warning count unchanged (47). Manual: on NIP-07, add a section
from the pool to compose and publish — events go out with real signatures and
relays accept them.

* FIXED — per-event Broadcast sent only the bare 30040 index, not the publication
:PROPERTIES:
:found: 2026-06-08
:branch: worktree-functional-finding-wind
:commit: cf5e8f9
:END:

** Symptom
Broadcasting a publication from the event modal's =Broadcast= action (the
button, or the =a b= chord) pushed only the single focused event. On a
kind-30040 publication index that meant the *index alone* went to the relays —
its 30041 sections and any nested 30040 indices were silently dropped, so a
reader fetching the broadcast index hit unresolvable =a= tags. The confirm
intent reflected this too: =Replicate 1 index= / =Broadcast 1 event=.

** Why
=EventViewModal.onBroadcastAction= unconditionally called =broadcastEvent= →
=POST /api/v1/broadcast=, which is a single-event fan-out (its legitimate job
for kind-0 metadata, relay lists, etc.). It had no notion of a publication tree.
The whole-tree path already existed — =broadcast_publication_handler=
(=POST /publications/:pk/:d/broadcast=) loads the depth-N tree, =collect_signed_events=
gathers index + sections + nested, and the =PublishManifest= on the =PublishIntent=
describes the full structure — but only the feed's "broadcast" pill used it.

** Fix
Route a kind-30040 broadcast through the publication endpoint:
- =EventViewModal.onBroadcastAction= branches on =n.kind === 30040 && dTag=,
  calling =broadcastPublication(pubkey, dTag, targets)= (whole tree) instead of
  =broadcastEvent=. Non-30040 events keep the single-event path.
- =broadcast_publication_handler= gained an optional =relays= body
  (=BroadcastPubRequest=) so the event modal keeps targeting the aggregator
  *broadcast* relay set; absent/empty falls back to the *publish* set, so the
  feed-pill broadcast is unchanged.
- The intent now notes the full structure (index + section counts, nested flag,
  per-event list) — it already did for the feed pill; this just routes the modal
  through the same manifest.

** Verify
=cargo build= / =cargo clippy= (no new warnings); =svelte-check --threshold error=
clean. Manual: open a 30040 index in the event modal, =Broadcast= — the confirm
intent reads =Replicate 1 index + N sections= (=· nested tree= when nested) and
=Broadcast N events=; every section + nested index lands on the relays.

* OPEN — kind 30002 published with =r= member tags instead of NIP-51 =relay=
:PROPERTIES:
:found: 2026-07-06 (during relay-deletion feature work)
:END:

** Symptom
=publishNamedSet= (RelaysBuffer.svelte) composes member relays as =["r", url]=
tags. NIP-51 specifies =["relay", url]= for kind 30002 relay sets — other
clients (Amethyst et al.) won't see our members. Ironically the pull side's own
comment documents this ("30002 carries URLs in `relay` tags; accept `r` as a
tolerant fallback").

** Note
The publish-diff endpoint (src/relay_diff.rs) already accepts both tag names
on both sides, so fixing the emit won't churn diffs. Fix = one-line tag-name
change + accept both on readers; consider re-publishing guidance for anyone
who already pushed an =r=-tagged set.

* FIXED — root/parent event fetch dies with raw =404= — never reaches relays in Confirm mode
:PROPERTIES:
:found: 2026-07-09 (clicking the 30023 root ref of a kind-1111 comment)
:branch: bugs/reader-discussion-fetch
:fixed-in: 442267d (engine/API intent gate) + 079e818 (web two-phase reader load)
:END:

** Symptom
Clicking a comment's root (a 30023 coordinate) shows
=Error: 404: {"event":null,"message":"Addressable event not found"}= — a raw
exception string, no loading state, no relay attempt, no way to retry. The
event is a perfectly fetchable addressable event.

** Why
=Engine::get_addressable= / =get_by_id= take no =mode_confirm= param, so they
hardcode a downgrade to =LocalOnly= whenever the engine isn't in Auto mode —
they can never emit a fetch Intent and never reach relays (unlike
=get_events_with_options=, which honors =mode_confirm || is_auto()=). Their
relay path also called =relay::fetch_addressable= directly, bypassing
FetchGuard activity tracking. On the web side, =fetchJson= throws
=`404: {...}`= and =ReaderBuffer= renders =String(e)=; its friendlier
not-found branch was dead code (the endpoint never returns 200-with-null).

** Fix
=get_by_id_with_options= / =get_addressable_with_options= delegating to
=get_events_with_options=; handlers grow =?confirm= and gate through
=begin_fetch_operation= (the =discussions_list_handler= pattern) so the
FetchConfirmModal intent flow applies. Web wrappers normalize 404 to
={event: null}=; ReaderBuffer does a two-phase local→relay load with a status
line and a human not-found message.

* FIXED — clicking a parent comment opens the generic reader, not the comment view
:PROPERTIES:
:found: 2026-07-09 (climbing a kind-1111 thread)
:branch: bugs/reader-discussion-fetch
:fixed-in: d8c7ae1 (k/K kind routing) + e9a31ad (discussion buffer confirm-gated load)
:END:

** Symptom
A comment's =parent= ref that is itself a kind-1111 opens as
=reader:event:<id>= — the comment gets wrapped as a fake single-section
publication (Prev/Next pager, =§= menu, "No comments or highlights found"),
with no root/parent rows, so the thread can't be climbed hop by hop.

** Why

buffer; there is no branch for "the target is itself a comment". The comment's
own NIP-22 =k= (parent kind) / =K= (root kind) tags already say what the
target is — no fetch needed to route correctly.

** Fix
Route by kind hint: =e=-refs with =k=/=K= = 1111/9802 open a
=discussion:<id>= buffer (same card, climbable); missing hint falls back to a
local-first =getEvent= kind check; everything else keeps the reader. Rule:
thread nodes → discussion view, true root → reader.
