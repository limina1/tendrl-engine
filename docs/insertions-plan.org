#+TITLE: Insertions, the Context Set & the Assistant — Design & Implementation Plan
#+DATE: 2026-09-16
#+STATUS: PLAN (branch design/insertions-context)

Three pieces of work that share one root cause — /reader-curated
collections that are not yet official structure/ — and therefore one
plan. Each could ship alone; together they make the "write more notes
from this one" loop coherent end to end, on both surfaces (in-app and
external agent over MCP).

* Where we are

Verified against the tree on 2026-09-16:

- *The in-app agent is built.* =src/tools.rs= has a 15-tool catalog
  (=catalog()=, =dispatch()=, =ToolPolicy= / =ToolCategory=) including
  =add_to_context=, =propose_section=, =edit_section=, =save_draft=,
  =publish=; =chat_agent_handler= (=src/api.rs=, =POST /api/v1/chat/agent=,
  SSE) runs the loop server-side. Design: =docs/ai-tools-architecture.md=;
  status: =docs/ai-assistant-status.md=. Branch =ai-context-tools= holds
  one unmerged docs commit (=5a84022=); the code is on master.
- *The MCP server is a stale mirror.* =scripts/tendrl-mcp.py= (stdio,
  =TENDRL_API= → =:3030=) hand-maintains its own 12-tool table and
  dispatch. It lacks =save_draft=; its =tendrl_get_context= (≈l.408)
  returns a /count string/, not the notes; its =tendrl_publish= forwards
  a =sign= boolean (≈l.434). Two catalogs, drifted.
- *Context is web-owned.* =web/src/lib/types.ts::ContextItem= (≈l.378)
  holds both the set (=source_addr=, =content=, =original_*=) and the
  flags (=in_context= / =in_compose= / =held=); =syncContext()= pushes a
  ={title, context_content}= projection via =PUT /api/v1/chat/context=
  into =chat.rs::injected_context=. The status doc records this as a
  decision; [[file:zettel/decision-context-set-engine-owned.org][reversed
  in half]] on 2026-09-16.
- *Signing is a boolean.* =PublishRequest.sign: bool= (=src/api.rs=
  ≈l.5898) signs as the /active/ identity. The assistant slot exists
  (=identity.rs::store_last_assistant=, ≈l.603) but no publish path can
  target it. Status doc open item 1 says "get the user's call" —
  [[file:zettel/decision-assistant-signs-own-key.org][given]].
- *NKBIP-01 is a priori.* Sections exist in a publication because the
  30040 lists them. Reader-attached matter has no wire format; comments
  and highlights are the nearest kinds and neither is promotable.
  Spec drafted: [[file:../nips/NKBIP-01-insertions.org][NKBIP-01 insertions]].
- *Subscription harnesses.* The status doc records that the OAuth /
  claude.ai-login path was explored and dropped (API key only). MCP is
  how a user's own Claude Code / Codex subscription reaches tendrl —
  the external harness brings its credential; tendrl holds none. The
  in-app path stays API-key.

* Design decisions

** D1 — One root cause, one object family
The context set, an insertion, a saved chat and an assistant-synthesized
zettel are all "curated, not official". Insertions get a wire format;
the context set gets engine ownership; both land in the same store
(=DraftStore= for review-first, signed-by-assistant for accumulate).

** D2 — Flags web, set engine
Per the [[file:zettel/decision-context-set-engine-owned.org][decision]].
=ContextItem= splits: =ContextEntry= (engine, persisted) + a web overlay
of flags keyed by entry id. =syncContext()= and =PUT /chat/context= are
deleted, not deprecated.

** D3 — Signing source is named, never inferred
Per the [[file:zettel/decision-assistant-signs-own-key.org][decision]].
=sign_as: "user" | "assistant"= replaces =sign: bool=. Agent tools pin
=assistant=. The user-facing composer keeps =user= (its existing
=SigningController= path — engine key / NIP-07 / NIP-55).

** D4 — Insertions are 30041 + NIP-22 anchors, not a new kind
Per the spec. Promotion is NKBIP-01 index republication; no promotion
event. Section-level anchoring only; span anchoring deferred to
[[file:zettel/idea-annotation-anchoring.org][annotation anchoring]].

** D5 — One tool catalog; the engine speaks MCP
=tools::catalog()= / =dispatch()= are the catalog. The engine exposes an
MCP endpoint (Streamable HTTP) serving that catalog under =ToolPolicy=.
=scripts/tendrl-mcp.py= is retired, or reduced to a stdio→HTTP shim
with /no/ tool table of its own. Claude Code, Codex, and the in-app
loop then call the same functions; =get_context= cannot be a stub
because it is =add_to_context='s sibling in one file.

** D7 — The annotations table: engine joins, client lays out
"3 of 100 users annotating" is a /query/, so the join is engine-side: the
table's header is a spell (=A:<index> k:30041 by:… count:by=), the author
histogram is a =count:= bucket, and a saved layout is a saved spell. The
client computes layout in a =$derived= (the =FocusGraph= idiom) and renders
cards with a keyed ={#each}= — Svelte's own data-join. No d3 by default;
=d3-force= alone (pure math, same =$derived=) only if free clustering is
wanted. Drag pins a card; positions are view state in =store.bufferState=,
never published. The table is *one* buffer kind (=annotations:<addr>=) with
its own views — by section · by author · timeline · free; beside the reader
or filling the window is the WM's split state, like any two buffers, not a
mode of the table. Canvas: Table page (the same buffer in two arrangements).

** D8 — "Create annotation" is one form with three doors
Section =⋮=, the =M= menu (anchored to the index = front matter), and a
/note/ variant of the highlight capture card (the selection travels as
=context=). The form is the 30041 MUST-haves — title, body, format — plus
one choice: /attach · insert before · insert after/. Anchor tags are
emitted by the engine; the wire preview comes from =/insertions/preview=
sharing the publish builder. Signs as the user; the assistant's derive
fills the same form under its own key. Canvas: Flow board 0.

** D9 — One structure, two skins, one narrow layout
The post-it treatment resolved on the canvas (2026-09-16): *B* (flat
margin card, left identity bar in =--id-local= yellow) is the structure;
*A* (tinted, taped, tilted) is a /skin/ on the same structure — a Settings
→ Appearance preference, not a fork; *C* is the narrow layout: below the
measure that leaves no gutter, attached notes and not-yet-subsumed
insertions fold into a 44 px row under their anchor and expand in place.
Canvas: Directions page (Main carries the flat/sticky tweak; the phone
board shows the folds).

** D10 — Bunker (NIP-46): the engine is the client
The user's key can live in a remote signer (nsecbunker, Amber-as-bunker,
=nak bunker=). The engine speaks NIP-46 itself: a =BunkerSigner= behind the
existing =IdentitySource::Nip46= slot — not the browser. Requests are
kind-24133 events to the remote signer's pubkey over the URI's relays,
NIP-44 v2 encrypted (=src/nip44.rs=, pure, from the =chacha20= / =hmac= /
=hkdf= primitives already in the tree; no NIP-04 fallback). A fresh
transport keypair is minted per connection and persisted in the OS
keyring with the =bunker://= URI, so a restart reconnects without the user
re-pasting. =auth_url= replies surface as a status the UI can open, never
a silent hang. Because =SigningController= is the one chokepoint, NIP-42
AUTH signs through the bunker too. The transport is a trait: unit tests
run the full connect / get_public_key / sign_event exchange against an
in-memory responder; the live check uses =nak bunker=.

** D11 — The assistant's publish path
=/api/v1/publish= takes =sign_as: "user" | "assistant"= (=sign: true= stays
as the user shorthand). A new =sign_draft {draft_id}= tool signs a saved
draft as the assistant and ingests it local-until-broadcast; the existing
=publish= tool (broadcast by id, Confirm-gated) is unchanged, so "signing is
the snapshot; broadcast is a separate step" holds for the assistant too.
The MCP =tendrl_publish= mirror sends =sign_as: assistant= and can never
name the user's key.

** D6 — The zettel bubble is one call, not an agent
Context assembled engine-side → one =run_turn= with a structured-output
schema (=output_config.format=) shaped like =ComposeState= → an insertion
template → signed by the assistant (or → =DraftStore=). No loop. Uses
=ClaudeProvider= (API key); never shells to =claude -p= — multi-second
startup on a popup.

* Order and size

0 → 1 → 2 → 3, then 4 ∥ 5 ∥ 5b, then 6. Phase 1 first because every later
phase reads the set; Phase 2 before 3 because assistant-signed
insertions are the point. Phases 4 and 5 are independent consumers of
1–3. Roughly: 1 and 3 are the real work; 2 is plumbing with a sharp
edge (the Extension threading); 4 depends on a Rust MCP transport
choice; 5 is mostly UI once 1–3 exist.

* Open questions (non-blocking; defaults stated)

- =insert= tag name — default keep; single-letter only if position ever
  needs relay-side querying (it does not).
- Promoted insertions keep anchor tags — default yes (provenance).
- MCP transport crate — evaluate =rmcp= vs a hand-rolled Streamable
  HTTP handler on axum; default hand-rolled if the crate pulls a
  runtime we do not already have.
- Should a saved =ContextSet= be publishable as a 30040 collection —
  out of scope; noted in the decision zettel.
- Table pan/zoom — none at first (scrollable table); =d3-zoom= or
  =panzoom= later if a 100-card table needs it.
- Model for the bubble — make configurable; try Opus 5 on real
  derivations before settling; latency vs synthesis quality is the
  user's call.
