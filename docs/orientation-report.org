#+TITLE: Tendrl as Reader, Writer, and Reference Manager
#+SUBTITLE: Orientation report — pattern survey, competitive evaluation, nostrdown state, and documentation reconciliation
#+DATE: 2026-07-05
#+STATUS: REPORT — point-in-time evaluation; action items at the end

* Purpose

The project's documentation still describes tendrl as "a local-first Nostr
backend implementing NKBIP-01" — a publication engine. That description is
now a subset of what the software is and where it is going. The accurate
framing:

#+begin_quote
Tendrl is a local-first *reader, writer, and reference manager* with Nostr
integration: a tool for reading structured publications, researching across
a distributed event network (structured search + semantic embeddings +
social discovery), composing and publishing NKBIP-01 publications, and
managing references through the nostrdown reference language — with
algorithmic fetching driven not only by author-side tags but by *post-hoc
labeling* (a reader comments on or labels an event with =#biology=; that
label becomes a retrieval signal for others).
#+end_quote

This report does four things:

1. Surveys the canonical software patterns of the reading / writing /
   research / reference-management category (Zotero, Readwise, Hypothesis,
   DEVONthink, Calibre, Citavi, Obsidian/Roam/Logseq, Zettelkasten,
   Bluesky/AT, folksonomy heritage, academic annotation layers).
2. Evaluates where tendrl stands against those patterns — what we already
   have, what Nostr gives us for free, what must be built deliberately.
3. Assesses the *nostrdown* branch (spec + implementation state + boundary
   debt + merge readiness).
4. Lays out the documentation reconciliation plan (per-file staleness audit
   summary; the full audit informed the actions in §7).

* The four-store model — and why Nostr fits it

Every mature tool in this category decomposes into the same four stores:

| Store                        | Zotero                   | Readwise     | Obsidian        | Tendrl (Nostr)                                            |
|------------------------------+--------------------------+--------------+-----------------+-----------------------------------------------------------|
| Source documents             | attachments              | docs/feeds   | vault files     | events in nostrdb (+ =document.rs= import)                  |
| Metadata records             | items                    | doc metadata | frontmatter     | event tags, kind 0 profiles, (spec'd) 30161 cites         |
| Annotation / knowledge layer | notes+annotations        | highlights   | (notes)         | 9802 highlights, NIP-22 comments, 1985 labels, ={{quote:}}= |
| Organization graph           | collections/tags/related | tags/views   | links/backlinks | 30040 indexes, nostrdown refs, tags, follow graph         |

The historically *painful* parts of the category are exactly what Nostr's
model natively solves:

- *Sync conflicts* (Zotero conflict storms, Calibre db corruption under
  folder sync) → signed immutable events; append-only; no mutable-record
  merge problem.
- *Exit rights* (Pocket shut down July 2025; unexported reading lists were
  permanently lost) → the local nostrdb copy *is* the archive; JSONL
  export already exists; the protocol is open. The tool is fully valuable
  at n=1 (the Pinboard lesson).
- *Layered visibility* (Hypothesis Only-Me/group/public) → keys + relays
  make visibility metadata, not architecture.
- *Revision history* (Gwern's git-backed "perpetual drafts") → replaceable
  events give signed, timestamped revision chains for free
  (=load_section_versions()= already exposes them).
- *Provenance on quoted/embedded fragments* (Xanadu's unfulfilled visible
  connection) → every embedded fragment is signed; author/date/origin
  chrome is nearly free (EmbedCard already renders it).

Conversely, the parts Nostr does *not* give us for free are the ones to
build deliberately: registry-backed metadata resolution, annotation
anchoring robustness, relatedness surfacing, resurfacing/review, and the
label-hydration machinery for post-hoc discovery. Those form the future
roadmap in §5.

Scorecard summary: *have 7, partial 9, spec'd 2, missing 12*. The "have"
column is concentrated exactly where the architecture made early bets
(library, search, composition-from-fragments, block addressability); the
"missing" column is concentrated in the *reader-side loop* (triage,
resurfacing, relatedness, backlinks) and the *social layer* (labeling,
WoT) — which matches the stated future orientation. Nothing in the missing
column fights the architecture; nearly all of it is a join or an index over
data the engine already stores.

* The nostrdown branch — state assessment

Branch =nostrdown= (44 commits ahead; =tendrl-web= is a direct ancestor, so
merge is a clean fast-forward). Verified against the worktree at
=.claude/worktrees/bright-dreaming-allen=.

** What is actually specified (spec drift from the brainstorm doc)

- The normative grammar lives in =docs/nostrdown-spec.md= (mid-conversion
  from =.org=, currently *uncommitted*), not =docs/nostrdown.org= (which
  remains the brainstorm).
- =nips/NKBIP-06.adoc= is *not* the nostrdown spec — it standardizes MIME
  =m=/=M= tags (relay-indexable =category/use-case/replaceability=), the tag
  vocabulary the other specs lean on.
- Citations are kind *30161* (=nips/NKBIP-03-revised-2.adoc=), one kind with
  =M=-tag source typing — not the four kinds 30–33 of upstream NKBIP-03,
  and not the 30030 sketched in the brainstorm doc.
- Presentation precedence standardized: per-reference modifier →
  publication =citation-style= tag → reader preference.

** Boundary debt (frontend/backend rule violations)

=web/src/lib/nostr/nostrdown.ts= re-implements Rust algorithms:
=normalizeSlug= (NIP-54 slugging twin of =nostrdown::normalize=),
=isMarkupLinkTarget= + =parseWikilink= (line-for-line ports), and the
token regexes exist in *two* TS copies (=nostrdown.ts= vs =nostrdown-cm.ts=)
that already disagree (one includes =slot=, the other doesn't decorate it).
The pre-resolution chip and editor decoration are a defensible carve-out;
the slug/link-target/wikilink *parsing* is algorithmic derivation that the
governing rule says resolves toward Rust (lightweight parse endpoint, or
ship parsed token spans with resolve responses).

** Merge readiness

- Fast-forwardable today; nothing on =tendrl-web= to reconcile.
- *Before merging*: commit the working-tree changes (the entire =[[ ]]=
  alias feature, the spec =.org= → =.md= conversion, NKBIP-03-revised-2
  edits) — the branch's committed state lacks =[[ ]]= support entirely.
- On merge, fix the stale CLAUDE.md nostrdown note (says =["wikilink",
  topic]= tags; code emits =["w", topic]=).
- Publish-path tag emission (=w=/=ref=/=a=/=q=/=p= appended at signing) is
  the substrate for backlinks and label joins — worth calling out in the
  merge commit as an interface other features will build on.

* Future patterns — prioritized recommendations

Ordered by leverage: how much existing substrate each reuses vs how much
new machinery it needs.

** Near term (mostly joins/indexes over data we already store)

1. *Merge nostrdown* (after committing the =[[ ]]= work); schedule the TS
   boundary-debt cleanup as a follow-up, not a blocker.
2. *Backlinks / "referenced by" panel.* Reverse index over =a=/=e=/=q=/=w=/
   =ref= tags in nostrdb; a =GET /api/v1/events/:addr/backlinks= endpoint and
   a reader pane. Pure Rust derivation, high reader value, cheap. This is
   the Obsidian killer feature and we already emit the forward edges.
3. *Post-hoc labeling v1 — the engine as AppView.* The Bluesky-shaped
   architecture: (a) user designates trusted labeler pubkeys; (b) engine
   subscribes to their kind-1985 (NIP-32) streams — and NIP-22 comments
   carrying hashtags, per the original use case; (c) labels are indexed
   locally and *joined onto events at query time*; (d) =label:biology=
   becomes a search operator, and "fetch events that people I trust
   labeled X" becomes a fetch mode ({kinds:[1985], authors:[…], #l:[…]}
   then hydrate targets). Free-form vocabulary, aggregate display — don't
   gate on a controlled vocabulary (folksonomies converge per-object).
4. *Semantic "See Also" pane.* Passive relatedness: k-nearest events for
   the section being read (HNSW query we already have), rendered as a side
   rail, with a *promote gesture* — one click turns a discovered neighbor
   into a ={{ref:}}= in the current draft. This is Obsidian's unlinked
   mentions upgraded by embeddings, and it closes the loop between
   research (discovery) and writing (durable structure).

** Mid term (new event kinds / new UI, still on-architecture)

5. [#B] *Citations (30161) implementation.* The spec is done; implement
   =RefKind::Cite=, citation-event emission from the composer, and
   =citation-style= rendering. Add *typed intent* modifiers
   (={{cite:x|supports}}= / =|contradicts= / =|extends=) — author-asserted,
   signed, aggregable into a per-target "3 supporting / 1 contradicting"
   badge (the scite.ai pattern; the rare contradicting edges carry most of
   the signal).
6. [#B] *Pin-vs-live staleness chrome.* ={{embed:naddr}}= (live) gets a
   "newer version exists" chip via =load_section_versions()=; explicit
   pin/live choice surfaced in the reference builder. MediaWiki's
   =$wgEnableScaryTranscluding= is the cautionary label: live transclusion
   of content you don't control needs visible version state.
7. [#B] *Reading states.* Inbox / Later / Archive on feed items — the
   Readwise triage pipeline. Local view state first; optionally NIP-51
   lists later. Archive ≠ delete; keeps the queue honest.
8. [#B] *WoT weighting.* Hop-distance over the local follow graph (kind 3)
   as a multiplier on label counts and search ranking; Vertex-style
   personalized PageRank as an optional external DVM. WoT scopes *who*,
   embeddings scope *what* — the intersection ("semantically near my query
   AND labeled by someone within 2 hops") is a discovery primitive none of
   the surveyed systems ships yet. That intersection is tendrl's most
   defensible novel feature.

** Longer term

9. [#C] *Resurfacing / daily review.* Scheduled re-presentation of past
   highlights/quotes with tunable decay (Readwise Daily Review) — the
   counterweight to a write-only archive.
10. [#C] *Registry metadata resolution.* On document import, look for
    DOI/ISBN in extracted text, query CrossRef/OpenAlex, and mint the 30161
    citation event automatically (Zotero's translator insight: metadata
    should arrive at reading speed, not typing speed).
11. [#C] *Materialized citation export.* Continuous BibTeX / CSL-JSON
    export of 30161 events (the Better BibTeX auto-export pattern) to plug
    into LaTeX/pandoc/Typst toolchains.
12. [#C] *Anchoring robustness.* When highlights/annotations target live
    (naddr) content, store the Hypothesis-style selector ensemble (quote +
    position) and add an explicit *orphaned* state instead of silent loss.
13. [#C] *Gwern-style publication status metadata.* A small tag vocabulary
    for draft/in-progress/finished + confidence on 30040s, rendered in the
    reader; pairs with the version-diff UI.

** Two negative results worth honoring

- Global graph views don't survive scale ("the hairball"). If a graph view
  is ever built, ship the 2-hop local neighborhood only.
- Centralized annotation buses die of economics (Crossref Event Data,
  sunset April 2026; del.icio.us). The durable design is reader-side joins
  and reader-side archives — which is the posture tendrl already has.

* Where tendrl is genuinely differentiated

Worth stating plainly, because the docs undersell it:

1. *Composition-from-fragments is native.* Citavi's Knowledge Organizer —
   the category's best writing model — is a proprietary single-project
   silo. NKBIP-01 makes the same model out of signed, globally addressable,
   reusable events. No surveyed tool has "sections composable into multiple
   publications by multiple authors with cryptographic provenance."
2. *The four historically painful problems are pre-solved* (sync, exit,
   visibility, revisions) by the substrate rather than by app code.
3. *Feed ≡ index.* A curated reading list, a Map of Content, and an
   algorithmic feed are one data type (30040). Curation becomes publishable,
   attributable, and subscribable — Bluesky needed a whole feedgen protocol
   for what falls out of NKBIP-01.
4. *WoT × embeddings intersection* (see §5.8) — no surveyed system has it.
5. *Local-first AI on the reading path* — in-process embeddings + LLM chat
   with context injection put tendrl ahead of everything surveyed except
   Readwise's Ghostreader, and without the hosted lock-in.

The honest weaknesses against incumbents: no metadata resolution against
scholarly registries (Zotero is untouchable here today), no
triage/resurfacing loop (Readwise), annotation anchoring is shallow
(Hypothesis), and the citation layer is paper — spec'd, not built.

says reader/writer/reference-manager, and (b) older subsystem/roadmap docs.
