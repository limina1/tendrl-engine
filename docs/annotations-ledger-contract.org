* What ships (one paragraph)

The annotations table stops being a canvas of fixed cards with five
layouts and becomes a *ledger*: one row per annotation, grouped
(§ · author · kind · time), each row opening in place — or in a detail
pane when the buffer is wide — with the full text, its per-kind actions
and its *thread* (kind-1111 replies). Two rows of chrome, every element
in them a filter: the spell input, *+ annotate*, the group-by segment,
rows|board, then the facets *who* (author bars) · *where* (§ counts) ·
*what* (kind counts) · *when* (a 21-day sparkline + all·7d·30d). A
request's answers nest under it (↳). Definitions carry their term and a
"glossary" flag. Hover lights the reader section; the § cell scrolls it.
*Board* keeps a card view (section columns, content-sized cards, no
pins). The reader folds each section's notes to a *strip of stubs*; a
stub opens the full card; the margin column is gone. The workflows hang
off the rows: annotate → request; an open request's row → *answer it
yourself* (one term at a time); a vocabulary request keeps *define a term
yourself* after it is answered; vocabulary mode → *define them myself*
(definitions with no request); a def row → relink / promote → glossary;
the ⑂ row → the *review buffer*, which takes the reader's place in the
split; every row → a reply (1111) or a *note in reply* (30041 with =q=).
Buffer kind =annotations:<root>=, the =SPC b o t= chord, the reader's
Tools *table N* and the WM split all stay.

* Engine API (Track A)

- =POST /api/v1/insertions= body gains =reply_to: Option<String>= — the
  coordinate of another annotation (a 30041 insertion, a definition, a
  request) in the same root. Emits =["q", <coordinate>, <relay hint or
  "">, <its pubkey>]= (NIP-18: a =q= value may be an address). The note is
  otherwise an ordinary insertion at the same anchor (=placement=
  attached). A =reply_to= outside the root is a 400.
- =POST /api/v1/insertions/load= rows gain =reply_to?: String= (the =q=
  coordinate when it names a 30041/30040 of this root's annotation set;
  other =q= tags are ignored) and the response gains
  =replies?: HashMap<String, usize>= — coordinate → number of kind-1111
  comments whose =A= (root scope) is that annotation's coordinate — when
  the body sets =replies: true=. One nostrdb query for the whole set
  (=kinds:[1111]= + =#A= over the loaded coordinates), local only; a
  =fetch_always= policy may add a relay pass but never blocks the load.
- =InsertionCounts= is unchanged (the *who* bars still read =by_author=).
- =propose_insertion= (MCP) accepts =reply_to= and documents it as "a note
  in reply to another annotation".
- Definitions without a request need nothing new (=role: definition=,
  no =request=).

Pure =reply_counts(&[LoadedInsertion], &[Note]) -> HashMap= with a unit
test; one assertion added to =test_insertion_propose_load_and_promote=
for =reply_to= round-tripping.

* Web model (Track B, =ledger-model.ts=)

#+begin_src typescript
export type LedgerKind = 'note' | 'def' | 'request' | 'mr' | 'kasten';
export type GroupBy = 'section' | 'author' | 'kind' | 'time';
export interface LedgerRow {
  id: string;               // coordinate, '818:<id>' or request id
  kind: LedgerKind;
  author: string;           // hex pubkey; '' for an unsigned request record
  parent: string;           // section coordinate, or the root
  sec: number;              // -1 = whole publication, else 0-based TOC ordinal
  placement: 'annotation' | 'before' | 'after';
  title: string;
  body: string;             // plain text for the board excerpt
  createdAt: number;
  status?: 'open' | 'answered' | 'merged' | 'declined';
  output?: 'notes' | 'kasten' | 'vocabulary' | 'ask';
  term?: string; glossary?: boolean;
  request?: string;         // the request this answers → nests under it
  replyTo?: string;         // a note in reply → "↩ <title>" on the row
  replies: number;          // kind-1111 count
  note?: LoadedInsertion; req?: AnnotationRequest;
}
export interface LedgerView {
  view: 'rows' | 'board'; group: GroupBy; sort: 'reading' | 'newest';
  detail: 'inline' | 'pane';
  by: string[]; secs: number[]; kinds: LedgerKind[];
  sinceDays: number | null; day: number | null;   // day = N days ago (sparkline pick)
  cursor: number; expanded: string | null; collapsed: string[];
  scroll: number;
}
buildRows(notes, requests, sections) → LedgerRow[]
groupRows(rows, sections, view) → { key, label, sec?, author?, rows }[]   // rules below
flatOrder(groups, view) → LedgerRow[]      // the cursor's order: a request's answers right after it (section grouping only)
facetCounts(rows) → { by, sec, kind, day[21] }   // over the rows the *other* facets admit
buildSpell(root, view) / parseSpell(text, root)   // by:, a:<section>, t:definition | t:annotation-request | k:818 | -t:…, since:
#+end_src

Grouping rules: *section* = one group per TOC row in reading order plus a
leading "whole publication" group; rows ordered requests, merge
requests, before, attached, after, then by time; answers (=request= set)
are not top-level rows but nest under their request. *author* = by
descending count (bars order). *kind* = requests · merge requests ·
definitions · kasten · notes. *time* = today · this week · this month ·
earlier, newest first. Empty groups are dropped. In author/kind/time
grouping every row is top-level (no nesting).

* DOM contract

Class names are the harness's selectors (Track F) and the walkthrough's
anchors; keep them verbatim. Colour is per author with the highlight
recipe (=pubkeyToColor=): the row rail, the dot, the bars, the thread
rail. Kinds get one glyph each: =◂= note (▴ before · ▾ after) · =def= ·
=?=/=✓= request · =⑂= merge · =⊞= kasten.

** Annotate window, answer mode (Track D)

- header "● answer — <request title>" + the request badge + "by · age",
  right: =.rq-count= "i of n · k to do"; the =×= closes.
- anchor chips + =.rq-chip--request= "request 30041:…".
- =.rq-term= row: =select.rq-term__pick= listing the request's terms
  (with " · defined by <name>" / " · signed by you" / " · skipped") and a
  last option "+ another term…" which swaps in =input.rq-term__new=;
  =select.rq-term__fmt= (markdown · org · asciidoc · plain).
- =.rq-warn= when the picked term already has a definition ("signing
  writes a second definition under your key; relink will ask which").
- =textarea.rq-def= the definition; style select; the event preview for
  this one event (=.rq-preview__pre=).
- footer: =.rq-btn--done= "cancel" (→ "done" once one was signed),
  =.rq-btn--skip= "skip ▸" (n > 1), =.rq-btn--sign= "sign ▸" (green
  =--green=): signs this one definition (=role: definition=, =request=
  pointer when answering, =sign_as: user=, =broadcast: false=) and pages
  to the next undone term; closes after the last. The request is closed
  (=answerRequest=) the first time anything is signed for it, with a
  summary naming what was signed and skipped.
- ask → the same window with the question as a fixed =.rq-term__fixed=
  title and "sign ▸" closing (a note with the pointer). notes/kasten →
  the composer with =request= (as today).
- vocabulary mode with ≥1 marked word gets =.rq-btn--define= "define
  them myself ▸" in the footer → answer mode over the marked terms with

- =RequestCard=: "answer it yourself ▸" stays on open requests and a

** Review buffer (Track E)

ledger is split beside a reader in the focused slot *replaces the
reader's leaf* (the mock: "the review takes the reader's place"); its
pane head has =.pane-head__back= "← reader" restoring the reader buffer
in that leaf. Elsewhere it opens as today.
- =.mr[data-mr][data-status][data-role]= root; =.rv= scroll body:
  =.rv__status= (badge · role · target · base "v3 · your current vN ·
  applies cleanly | you have moved on — rebased" · sent-to), =.rv__ask=
  (the 818 content with the requester's rail; source line), =.rv__sum=

  (summary: title · d · hunks · +a tags; =DiffBlock= inside),

  today), =.thread= (=AnnotationThread= on the 818: =coordinate= =
