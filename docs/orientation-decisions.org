* 1. Mission & identity

** The mission statement

The headline self-description in README.md, CLAUDE.md, project-summary.org,
and features.org still says "publication engine." Whatever wording is
chosen here gets hoisted into all four. Proposed text:

#+begin_quote
Tendrl is a local-first *reader, writer, and reference manager* built on
Nostr: read structured publications, research across a distributed event
network (structured search, semantic embeddings, social discovery), compose
and publish NKBIP-01 publications, and manage references through the
nostrdown reference language. Fetching is algorithmic and reader-driven —
not only author-side tags, but post-hoc labels: when someone you trust
reads a document and labels it =#biology=, that label becomes a retrieval
signal for you.

** Emphasis ordering: reader-first, writer-first, or research-first?

The three words in "reader, writer, reference manager" are not neutral —
the order implies where UI defaults and roadmap energy go. The current
codebase is strongest as a *writer* (compose is the most mature surface);
the missing-pattern analysis says the biggest gaps are in the *reader loop*
(triage, resurfacing, relatedness, backlinks); the novel differentiators
(WoT × embeddings, post-hoc labeling) are *research* features. Picking an
emphasis decides, e.g., whether the default landing buffer is the feed
(reader), the composer (writer), or search (research), and which quarter
gets which feature cluster.

- [ ] Reader-first
- [ ] Writer-first
- [ ] Research-first
- [ ] Deliberately balanced (no default emphasis)
Notes:

** Anti-goals, formalized

The publishing philosophy ("deliberate publishing + reference management,
NOT social broadcast") exists as a working principle but isn't written into
canon. Formalizing anti-goals prevents drift and makes review decisions
cheaper ("does this feature serve broadcast? then no"). Candidate
anti-goals, each its own checkbox:

- [ ] *Not a social broadcast client* — no engagement mechanics, no
  auto-publishing of lists/relay sets, no notification treadmill.
- [ ] *Not a relay browser* — tendrl reads what its policies fetched, and
  makes the partiality visible; it does not promise "the whole network."
- [ ] *Not a hosted service* — fully valuable at n=1, offline; the local
  copy is the archive (the Pinboard/Pocket lesson).
- [ ] *No global graph visualization* — local 2-hop neighborhood views
  only, if any (the Obsidian hairball lesson).
- [ ] Other anti-goals (write below)

* 4. Reader-loop features

** Backlinks / "referenced by" panel

The Obsidian pattern: store links one-way, render them two-way via a
derived reverse index. The forward edges already exist — the publish path
appends =w=/=ref=/=a=/=q=/=p= tags to every signed section — and nostrdb can
answer the reverse query. Engine work: a backlinks endpoint (reverse index
over =e=/=a=/=q=/=w= tags for a given id/naddr); web work: a reader side-pane.
Pure Rust derivation, no new stored state, and it's the feature that makes
the reference graph *visible* rather than write-only.

- [ ] Include
Priority:
Notes:

** Semantic "See Also" pane + promote-to-ref gesture

DEVONthink's See Also (passive relatedness) fused with Obsidian's unlinked
mentions (discovery → one-click promotion to explicit link), upgraded by
embeddings we already run: while reading or composing a section, a side
rail shows k-nearest events from the HNSW index; one gesture inserts a
={{ref:}}=/={{embed:}}= to a neighbor into the current draft. This closes the
research→writing loop and is the first feature that makes the embedding
index *ambient* instead of query-gated.

- [ ] Include
Priority:
Notes:

** Reading states: inbox / later / archive

The Readwise triage pattern: separate "is this worth my time" from reading
it; archive without guilt (archive ≠ delete, stays searchable). Today the
feed has no per-item reading state and the ignore list is the only triage
tool. Design question to settle in Notes: local-only view state (cheap,
private, no protocol surface) vs. NIP-51 lists (portable across clients,
but publishing reading behavior collides with the deliberate-publishing
philosophy — could be local-first with explicit opt-in publish).

** Resurfacing / deliberate review

The counterweight to a write-only archive (Readwise Daily Review): a small
scheduled dose of past highlights/quotes/sections, with keep/discard
feedback and tunable decay. Without it, the highlight and quote layer
accumulates and is never seen again. Fits naturally as a buffer type in
the WM shell ("review buffer"), fed by an engine endpoint that samples from
9802s/quotes/notes weighted by age.

Companion to the §3 pin/live formalization: naddr-addressed embeds and
imported reference blocks get a "newer version exists" chip; clicking shows
a version diff (substrate: =load_section_versions()= + the republish-diff
transform already in Rust). Readers see drift instead of silently reading
stale transclusions; authors see when their imports moved.

** Publication status & confidence metadata

Gwern's pattern: every long-lived document carries visible status
(draft / in-progress / finished), a confidence marker, and a date range —
"perpetual drafts" made legible. Nostr gives the revision chain for free;
this adds a small tag vocabulary on 30040s (e.g. =["status", "draft"]=,
=["confidence", "likely"]=) rendered in the reader header and feed cards.
Cheap, and it sets cultural expectations for accretive writing.

* 5. Reference-manager features

** Implement citations (kind 30161)

The spec (NKBIP-03-revised-2) is done; the code is absent — ={{cite:}}=
parses as literal text. Work: =RefKind::Cite= in the parser, citation-event
emission from the composer (a "cite this" flow that mints or reuses a 30161
with title/author/published_on/accessed_on and the quoted passage in
content), resolution + rendering per the =citation-style= precedence. This
is the feature that makes "reference manager" true in the Zotero sense
rather than aspirational.

- [ ] Include
Priority:
Notes:

** Typed citation intents

scite.ai's finding: ~92.6% of citations merely mention; the rare
supporting (6.5%) and contradicting (0.8%) edges carry nearly all the
signal. As a nostrdown modifier — ={{cite:smith-2024|supports}}= /
=|contradicts= / =|extends= — the intent is author-asserted and signed
(more reliable per-edge than scite's ML), and aggregates per target into a
"3 supporting / 1 contradicting" badge on any cited event. Differentiating
and cheap once 30161 exists; also the semantic-roles idea from the original
brainstorm, landed in its minimal viable form.

- [ ] Include
Priority:
Notes:

** Registry metadata resolution on import

Zotero's deepest moat: metadata arrives at reading speed. When
=document.rs= extracts text, scan the first pages for DOI/ISBN, query
CrossRef/OpenAlex, and mint the 30161 citation event (and index metadata
tags) automatically — the imported PDF arrives *already citable*. Network
access must respect Confirm mode (registry queries are fetch intents like
any other). Without this, every citation is hand-typed and the reference
manager loses to Zotero on day one for academic corpora.

- [ ] Include
Priority:
Notes:

** Materialized citation export (BibTeX / CSL-JSON)

Better BibTeX's lesson: stable human-meaningful keys + continuously
materialized export is what plugs a reference manager into external
toolchains (LaTeX, pandoc, Typst). A =GET /api/v1/citations/export= (bibtex
| csl-json) over local 30161 events, with the nostrdown d-tag as the
citekey, makes tendrl a usable bibliography source without any editor
integration work.

- [ ] Include

** Annotation anchoring robustness + orphan state

Hypothesis's engineering lesson: no single selector survives document
change; store an ensemble (exact quote + prefix/suffix + position) and
re-anchor through a strategy cascade; when confidence fails, the
annotation becomes *orphaned* — kept and flagged, never silently lost.
Tendrl's immutable event sources sidestep most drift, but highlights on
live (naddr) content face it on every republish. Work: store quote+offset
selectors on 9802s we create, re-anchor across versions, add an orphaned
display state.

* 6. Social discovery & post-hoc labeling

** Labeler subscription + hydration join (the core architecture)

Bluesky's stackable moderation, generalized to enrichment, is the
architecture worth stealing wholesale: labels are signed third-party
events about content the labeler doesn't own; clients *choose* labelers;
an AppView joins labels onto content at hydration time. Tendrl's engine is
positioned to be its own AppView: (1) the user designates trusted labeler
pubkeys; (2) the engine subscribes to their label streams; (3) labels are
indexed locally; (4) every event the API serves carries its known labels,
joined at query time in Rust. This is the machinery under the original
use case: someone reads a document, comments =#biology=, and that becomes a
retrieval signal.

- [ ] Include
Priority:
Notes:

** Which events count as labels?

Sub-decision for the above. NIP-32 kind-1985 events are the formal
analogue of a Bluesky label (namespaced =L=/=l= tags, explicit target).
But the original tendrl use case is *comments* — a NIP-22 (kind 1111)
reply carrying =#biology= or a =t= tag. Options, checkable independently:

- [ ] kind-1985 (NIP-32) label events — the formal channel
- [ ] NIP-22 comments carrying =t= tags / hashtags — the organic channel
- [ ] kind-1 quotes/mentions with hashtags — noisier, wider net
- [ ] 30040 index membership — "someone included this in a curated index"
  as an implicit label (strongest signal of all: curation as labeling)

** =label:= search operator + fetch-by-label mode

The retrieval surface for the label layer: =label:biology= (optionally
=label:biology@npub…= scoped to a labeler) as a search token compiling to a
1985/tag filter + target hydration, and a fetch mode "pull events that my
labelers marked X" as a first-class algorithmic fetch alongside
LocalFirst/FetchAlways. Free-form vocabulary, per the folksonomy evidence
(per-object tag distributions converge without enforcement) — aggregate
and display, don't gate.

- [ ] Include
Priority:

** WoT weighting

The sybil answer for an open network: weight labels, search results, and
discovery by the labeler's position in *your* social graph. Insertion
points, checkable independently:

- [ ] Query-time scope filter: only labels/results from ≤k hops (local
  follow-graph walk over kind-3s — no external dependency)
- [ ] Ranking multiplier: hop-distance or personalized-PageRank score
  weights label counts and search order
- [ ] External WoT service (Vertex-style DVM) as an *optional* provider —
  keep the local walk as the default so n=1 still works
- [ ] Wiki/nostrdown resolution ladder position (ties into §3 scoping)

The intersection play — "semantically near my query AND labeled/written
within 2 hops" — is a discovery primitive none of the surveyed systems
ships, and both halves (HNSW index, kind-3 graph in nostrdb) are already
local.

** Algorithmic feeds as 30040 indexes

Bluesky's deepest structural idea: a feed generator returns only an
ordered list of references; hydration happens elsewhere. In tendrl, a
curated reading list, a Map of Content, and an algorithmic feed are
already the same data type — a 30040 over event addresses. Proposal: any
internal algorithm (semantic neighbors, label queries, WoT-scoped
discovery) can *emit its results as a local 30040*, making algorithm output
saveable, publishable (deliberately), diffable, and subscribable like any
other publication. Curation becomes an artifact, not a session.

- [ ] Include
Priority:
Notes:

** Annotation follows the identifier (badge join everywhere)

PubPeer's pattern: the annotation layer travels with the identifier, not
the venue — wherever the paper appears, the "has comments" badge appears.
Generalized: whenever *any* event renders anywhere in tendrl (feed card,
search result, embed card, reader header), join and badge its known
post-hoc layer — comment count (shipped for sections), labels, highlight
count, supporting/contradicting citation tally. One engine-side join, one
badge row component, applied uniformly.

* 8. Open questions (no proposal attached — text entry only)

** Private / encrypted layers

Everything above assumes public events. Private highlights, private
reading states, private labels (NIP-44-encrypted, signer-dependent —
under NIP-07 the decrypt lives in the browser) are architecturally
different enough that retrofitting is painful. When does private-layer
support enter the roadmap, and which layer first (highlights? reading
states? labels?)?

Notes:

** Multi-user direction vs. the reference-manager framing

docs/multi-user-architecture.org sketches multi-tenant directions. A
reference manager is intensely personal (n=1); group libraries (Zotero
groups, Hypothesis groups) are the collaborative variant. Does the
multi-user work serve "shared library" semantics, or hosting convenience,
or both — and does it change any §6 decisions (e.g., whose follow graph
scopes WoT in a shared instance)?
