#+TITLE: Idea: audiobooks — TTS per section, Blossom storage, NKBIP-07 indexes
#+TYPE: idea
#+STATUS: plan (research done 2026-11-09, branch feat/audiobook-blossom open)
#+DATE: 2026-11-09

* The ask

Read a publication aloud. Generate narration per section with ppq.ai's TTS,
store the audio on Blossom, publish an event tree that maps each recording
to the section (and version) it narrates, and let any reader of the book
discover, play, and mirror those recordings.

* Research (what the specs actually give us)

** ppq.ai TTS (=POST https://api.ppq.ai/v1/audio/speech=, Bearer key)
OpenAI-compatible body: =model=, =input=, optional =voice=, optional
=language= (ISO 639-1; 422 on voice/language mismatch). Output is an audio
body — the docs only ever show =.mp3=; =response_format= is undocumented.
=GET /v1/audio/models= (no auth) returns per-model pricing; =GET
/v1/audio/voices?language=en= (no auth) the voices.

| model                 | api price / 1k chars | input cap per call |
|-----------------------+----------------------+--------------------|
| =deepgram_aura_2=     | $0.0158              | 2000 chars         |
| =eleven_flash_v2_5=   | $0.0422              | 5000 chars         |
| =eleven_multilingual_v2= | $0.1899           | 5000 chars         |
| =tinfoil-voxtral-tts= | $0.0042 (min $0.0021 per 1200-char chunk) | 1200 chars |

Consequence: every section must be *chunked at sentence boundaries* into
≤cap pieces, one call each, then joined. The existing =ProviderRegistry=
(=src/providers.rs=) already holds the ppq key, balance, and the
=needs_funding= ceiling gate — TTS is a second spend path on the same
account, not a new provider. (No =providers.json= exists in the local data
dir today: the account has to be created/funded in the agent-services
modal before any generation runs.)

** Blossom (hzrd149/blossom, BUD-01…12)
- BUD-01 =GET /<sha256>.ext= with range requests + CORS =*= → the browser
  can stream straight from the server; no engine proxy for playback.
- BUD-02 =PUT /upload= (raw bytes, =Content-Type=, optional =X-SHA-256=) →
  blob descriptor ={url, sha256, size, type, uploaded}=; BUD-06 =HEAD
  /upload= preflight. BUD-08 may add a =nip94= tag array.
- BUD-11 auth: a signed **kind 24242** event, =t= verb (=upload= / =get= /
  =delete= / =list= / =media=), =expiration=, one or more =x= (sha256),
  optional =server=, sent as =Authorization: Nostr <base64url>=. Upload and
  mirror *require* =x=, so the hash is known before signing.
- BUD-04 =PUT /mirror= with body ={"url": …}= and the *same* upload token →
  the server pulls and verifies against =x=.
- BUD-03 kind 10063 =["server", url]…= = a user's server list, ordered;
  clients extract the hash from a dead URL and retry the author's servers.
- BUD-10 =blossom:<sha>.<ext>?xs=&as=&sz== URI.
- BUD-07 402 + =X-Lightning= / =X-Cashu= for paid servers.
- blossom.band is live and answers =HEAD /upload= with 401 "authorization
  required" — i.e. open to any signed pubkey until proven otherwise;
  quotas unknown until a real upload.

** NKBIP-07 — Hierarchical Blossom Piece Indexes (the referenced note)
{{ref:30817:fd208ee8c8f283780a9552896e4823cc9dc6bfd442063889577106940fd927c1:nkbip-07|NKBIP-07}}
by Silberengel: **kind 32176**, parameterized replaceable, the NKBIP-01
shape applied to blobs. =d= + =title= required; =a= tags are *child 32176
indexes only*; =b= tags are ordered piece hashes =["b", sha256, bytes]=;
=x= = full-file digest, =size=, =type= (=media=), =blossom= server hints,
=image=, =t=, =T=/=N= slugs; =content= may hold a transcript with
=transcript= ∈ {txt, vtt, srt, json}. ≤1000 =a=, ≤1000 =b= per event.
Assembly: local =b= first, then each =a= child, recursively.

What it does *not* define: a tag that says "this index narrates / is a
rendition of Nostr event X". That is the gap this feature fills (below),
and it should go back to the NKBIP-07 author as a proposed extension.

* Data model (proposal)

One 32176 tree per narration, mirroring the 30040 tree:

#+begin_example
root 32176  d=<nanoid>  title="<book title> (audio, <voice>)"
  A  30040:pk:d              ← the publication (live coordinate)
  E  <30040 event id>        ← the exact index version narrated
  K  30040
  blossom https://blossom.band
  type media · m audio/mpeg · voice · model · lang
  a → leaf 32176 per section, in TOC order (label = section title)

leaf 32176  d=<nanoid>  title="<section title>"
  A  30041:pk:d              ← the section coordinate
  E  <30041 event id>        ← the version whose text was spoken
  K  30041
  b  <sha256 of the joined mp3>  <bytes>
  x  <same sha256> · size · duration · m audio/mpeg
  blossom https://blossom.band
  content = spoken plain text (transcript txt)   [optional, default on?]
#+end_example

- =A=/=E=/=K= are the NIP-22 / NKBIP-01-insertions scope letters already
  used in this codebase for "the event this is about"; they are
  single-letter so =#A= / =#E= are relay-indexable (nostrdb packs 64-hex
  tag values as ids, so =#E= works locally too — see =git.rs=). They do
  not collide with NKBIP-07's =a= (children) or =e= (unused).
- Discovery for step 2 is therefore one filter per tree node:
  =kinds:[32176], #A:[coord]= → every narration by anyone, any version.
  Ranking: =E= equals the loaded event id (exact text) → same =A= with a
  different =E= (another version, marked stale) → by created_at.
- One chapter = one joined blob (one =b=). The ≤cap TTS chunks are a
  generation detail; we do *not* publish them as separate pieces, so a
  section plays from a single =<audio src>=. "Play the whole book" is
  sequential leaf playback from the root, not a second concatenated blob.
- Joining MP3s: ppq returns MP3 (format unselectable so far). Pure-Rust
  frame concatenation (strip ID3v2 + the Xing/Info frame off chunks 2..n,
  same model/voice/bitrate throughout) is portable to Android; ffmpeg is
  not a runtime dependency we can assume.
- Spoken text comes from the section's content after stripping its =m=
  markup and nostrdown tokens (engine-side: tokenizer exists; markup→text
  pass is new).

* Workflow

1. *Generate* (author, costs money): reader → tools → "Narrate". Engine
   walks the 30040 tree, builds spoken text per section, shows a cost
   estimate (chars × model price) behind the same ceiling gate as chat
   turns, then per section: chunk → N calls → join → sha256 → sign 24242
   =upload= (user's active signer; a =BlossomSigner= beside =AuthSigner=,
   kind 24242 only) → =PUT /upload= → leaf 32176 template → sign →
   ingest (local-until-broadcast) → root 32176 last. Progress over SSE
   like the publication stream. Resumable: a leaf whose =E= + voice
   already exists locally is skipped.
2. *Pull* (any reader): when the publication tree streams, the engine
   also queries =#A= for the root and each section (LocalFirst; relay
   backfill Confirm-gated) and ships the ranked recordings per node — a
   new =PubLoadEvent::Audio= (or a sibling endpoint) so the browser never
   ranks versions itself.
3. *Mirror*: a recording's menu → "Mirror to my server": engine signs a
   24242 =upload= token with that =x= and =PUT /mirror {url}= to a server
   from the user's Blossom set. Open: whether to also publish the user's
   own 32176 (same =A=/=E=, own =blossom= hint) so others find the copy,
   or leave it as a local-availability win (BUD-03 says readers retry
   the *uploader's* 10063 list, which the mirrorer is not on).
4. *Play*: events first, bytes on demand. Per-section ▶ in the reader,
   ▶ on the root for sequential play; one =<audio>= element fed the leaf
   URL list; URL = =blossom= hint + =/<sha>.mp3=, fallback across the
   user's and the author's (10063) server lists by hash per BUD-03.
   Playback position is view state (frontend).

* Settings / stores

- A local Blossom server set (=<data_dir>/blossom.json=, same pattern as
  =relays.json=): upload targets, mirror target. Seed from the user's own
  kind 10063 as a *suggestion*, never auto-publish one
  ([[file:decision-engine-owns-provider-credentials.org][credentials stay
  engine-side]], publishing philosophy).
- TTS defaults: model, voice, language; per-run override.

* Open questions

- Confirm with the NKBIP-07 author that =A=/=E=/=K= on a 32176 is the
  blessed way to bind an index to the event it renders (vs a new tag).
- Whether ppq honours =response_format= (opus/ogg would shrink blobs
  ~3×) — probe once an account exists.
- blossom.band quotas / per-pubkey limits for multi-MB audio.
- Transcript in =content= on by default (search finds spoken text; doubles
  relay bytes) or off.
- Should a narration of a 30040 that nests other 30040s produce one tree
  or one per sub-publication (reuse when a sub-book is already narrated)?
