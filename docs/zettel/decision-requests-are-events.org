#+TITLE: Decision: Annotation Requests Are Records the User's Agent Reads — Never a Harness
#+TYPE: decision
#+STATUS: current
#+DATE: 2026-09-17

* The decision

"Ask for notes about this place" does not make tendrl drive a model. A
request is a *record*: a local file (=<data_dir>/requests/=) with the
anchor (publication + section, like an insertion), the task, scope
hints, an optional excerpt — unsigned by default, so it needs no
identity. Optionally the user signs it as a *kind-30041 annotation on the
section* — the same shape as the notes that will answer it, anchored the
same way (=A=/=a=/=e=), marked =t: annotation-request= and carrying its
metadata as tags (=scope=, =output=, =context=, =style=) — and optionally
broadcasts it; *local is the default*. Whoever answers reads open
requests through =list_requests= over MCP, writes assistant-signed
insertions that carry =["request", <request coordinate>]=, and closes a
record with =answer_request=. A signed request is *answered iff* a local
30041 points at it — derived from the store on every read, never
recorded; no reply event, no assistant identity needed at ask time.
(Amended 2026-09-17: the first cut signed the request as a kind-1111
mention of the assistant with a 1111 reply closing it; the user's call
was that the ask should be the same kind of thing as the answer, and the
answer should point at the ask.)

No queue tendrl pushes into, no stream a session must hold open, no
process that wakes Claude Code. The user types "check tendrl requests"
in their own harness; the =/tendrl-requests= skill
(=docs/skills/tendrl-requests/=) is the loop. (User's call, 2026-09-17.)

* Why

- *The line is who initiates.* An app that wakes a Claude Code session
  and hands it work is using the subscription as its backend — the
  thing the Agent SDK terms disallow and the thing the user is being
  careful about. An app that writes a note the user later tells their
  agent to read is a filesystem and a protocol. Same result, honest
  shape.
- *Async by nature.* Reading, thinking of the question, and getting the
  answer are hours apart anyway. Nothing is lost by not being live.
- *It composes with Nostr.* A signed request is an ordinary annotation:
  the reader loads it with the notes (=insertions/load= tags it
  =role: request=), the answers point at it, anyone's NKBIP-01 client
  sees the ask beside the section and the notes beside the ask. Unsigned
  stays private.
- *The in-app loop keeps the same input.* When it answers requests
  later (API key, the user's own cost), it reads the same records —
  one shape, two answerers.

* Consequences

- The zettel bubble (plan Phase 5) is /requests + insertions/, not a
  derive endpoint that calls the model. An engine-side answerer is a
  later, optional step with the same contract.
- Annotate mode is a second capture toggle beside highlight mode; the
  event menu's *Ask* (=q=) is the click door.
- =answer_request= records coordinates for a record; the reader renders
  them as pending cards through the ordinary =load annotations= pass. A
  note's =request= tag is the durable link: the card wears an "↳ answers"
  chip that opens the request, and the request card lists the notes that
  point at it whether or not a record was ever closed.
- The annotations table (plan Phase 5b,
  [[file:feat-annotations-table.org][feat-annotations-table]]) draws a
  request as a card with a badge — "? request", "✓ request · answered"
  once a note points at it — and the answering note wears an "↳ answer"
  chip, all from the same pointer; no request-specific store to join.
  Requests are asks, not notes: the table's author histogram
  (=insertions/load= =counts=) and the reader's *table N* count exclude
  =role: request=, and the reader no longer counts a request-30041 as a
  pending note. An unsigned record has no author and files under an
  /unsigned/ bar.
