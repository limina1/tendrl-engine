#+TITLE: AI Assistant
#+TYPE: feature
#+STATUS: partial
#+DATE: 2026-07-05

A writing assistant with server-side tool-calling over the Nostr corpus: the
engine runs an agentic loop in which the model searches, reads, curates
shared context, composes, fetches from relays, and (opt-in) publishes.
Shipped per =docs/ai-assistant-status.md=. *Since 2026-09-22 the model is an
agent service* — ppq.ai or a routstr node, set up and funded in the app
(=docs/agent-service-flows.org=) — the Anthropic API-key provider was
removed; Claude reaches tendrl only as an external harness over MCP.
Next epoch planned on =design/insertions-context= —
[[file:../insertions-plan.org][the plan]]: engine-owned context set, named
signing source, insertions, the engine speaking MCP, the zettel bubble.

* What exists
- Typed chat fragments (system/user/assistant) with edit mode — collapse to a
  single delimited buffer, edit freely, re-parse on exit (=src/chat.rs=, pure
  state; =sanitize_tool_pairs= keeps tool_use/tool_result pairing valid).
- Context set, engine-owned (2026-09-16, plan Phase 1): =src/context.rs= —
  =ContextSet= / =ContextEntry= (source: event | addr | literal; content +
  captured =original=; tags; origin user/assistant/chat/import), persisted
  at =<data_dir>/context/active.json= (survives a restart; a chat reset keeps
  it) plus named snapshots under =context/sets/=. API =/api/v1/context=
  (GET · DELETE), =/context/entries= (POST by id/addr/literal — same
  resolver as the tool), =/context/entries/:id= (PATCH edit/reset · DELETE),
  =/context/sets= (list/save/load/delete). =ChatState.context= is the one
  owner; =to_agent_messages= renders it. The web keeps only routing flags:
  =ContextPanel= renders the engine entries through =entryAsItem()= with
  =in_compose= / =held= overlaid from the linked pool item, and every
  membership change is an engine call followed by =refreshContext()=, which
  re-mirrors =in_context= onto the pool. Decision:
  [[file:decision-context-set-engine-owned.org][context set is engine-owned]].
- =LLMProvider= trait (=src/llm.rs=): =OpenAiCompatProvider= (ppq.ai /
  routstr nodes) + =NoopProvider=; provider-neutral =ContentBlock= /
  =AgentMessage= / =run_turn()= types. Accounts, balances, discovery and
  the per-turn funding gate: =src/providers.rs= + =/api/v1/providers=.
- Agentic loop: =chat_agent_handler= (=src/api.rs=, =POST /api/v1/chat/agent=,
  SSE); tool catalog + dispatch in =src/tools.rs= (18 tools: search, read,
  NKBIP-01 views, =fetch_from_relays=, =add_to_context= / =get_context= /
  =remove_from_context= — these write the engine-owned set directly through
  a =ToolCx= (engine + chat handle), no web fold-in — compose-write,
  =get_identities= (the assistant's own pubkey/npub/signer source + the
  user's, with the =by:assistant= / =by:me= hints — 2026-09-22),
  =publish_publication= (sign as the assistant — engine key or bunker —
  store, and broadcast in one call; =kind= + =content= for an atomic
  30023/30818; 2026-09-22), =sign_draft= (signs a saved draft AS THE
  ASSISTANT, local-until-broadcast), =publish= (broadcast one =id= or a
  batch of =ids= under one confirmation)). =ToolPolicy= filters the catalog
  before the provider call — default is *every* tool since 2026-09-22
  (Publish included: the assistant publishes under its own identity, and
  Confirm mode still gates each broadcast); the AI Tools settings tab can
  switch any off. =prompt.md= carries a "Who you are" section so the model
  knows it has its own identity and how to publish.
- Gating reuses the Confirm-mode modals; saved sessions (=src/sessions.rs=);
  editable =prompt.md= system prompt.

* Gaps / open edges
- Standing note — *tool-use parity*: any capability a user has through the
  API that the assistant cannot invoke as a tool is a gap to log here. The
  assistant should be able to publish, search, and manage knowledge in
  parallel with the user.
- AI-authored signing *shipped* (2026-09-16, plan Phase 2): =sign_draft=
  signs with =Engine::assistant_signer()= (the assistant session — never
  the user's key); =/api/v1/publish= takes =sign_as=; the MCP
  =tendrl_publish= sends =sign_as: assistant= and cannot name the user.
  Tested: an assistant publish carries the assistant's pubkey, a user
  publish the user's. [[file:decision-assistant-signs-own-key.org][Decision]].
  The assistant has its own =SigningController=: an engine-side key *or* a
  bunker (=/assistant-identity/bunker/…=, e.g. a second Amber account, an
  nsecbunker key) — and on the Android host direct Amber (NIP-55) through
  the same handlers mounted under =/assistant-identity/= (device test
  pending). [[file:decision-bunker-engine-is-the-client.org][Decision]].
- One tool catalog: =src/tools.rs= (21 tools) serves both the in-app
  loop and, since 2026-09-17, the engine's own MCP endpoint (=/mcp=,
  [[file:feat-mcp.org][feat-mcp]]) under the same live policy;
  =scripts/tendrl-mcp.py= is a stdio shim with no tool table. This is how
  a user's own Claude Code / Codex subscription reaches tendrl — the
  external harness brings its credential, tendrl holds none (the OAuth
  path was dropped; API key only for the in-app loop).
- Live-reference and compact-handle context modes unbuilt.
