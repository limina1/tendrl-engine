#+TITLE: Network Modes & Fetch Policy
#+TYPE: feature
#+STATUS: implemented
#+DATE: 2026-07-05

Local-first network control: the user decides when the engine talks to
relays, per-query (fetch policy) and globally (network mode). Nothing hits
the network without either a policy that allows it or an explicit approval.

* What exists
- =FetchPolicy= (=src/engine.rs=): =LocalOnly= (nostrdb only, instant,
  offline), =LocalFirst= (local, then relay backfill if under limit — the
  default), =FetchAlways= (always hit relays, merge with local).
- =NetworkMode= (=src/network.rs=): =Auto= — user-initiated relay fetches run
  automatically; =Confirm= — every user-initiated fetch emits an *intent* the
  UI must approve before the engine proceeds. Note: older docs called these
  "Online" / "Offline"; =Auto= / =Confirm= are the current names.
- Intents + live fetch activity stream to clients over SSE
  (=GET /fetch-events=); approval via a confirm endpoint;
  =GET /api/v1/network/status= / =POST /network/mode= for state.
- =FetchGuard= RAII tracks in-flight relay requests in a ring buffer
  (=NetworkActivity=) so the UI shows live activity.
- Web: network-mode toggle in the header, modeline network pill with a
  pulsing "fetching" dot, =FetchConfirmModal= and =FetchActivityModal=
  (=web/src/lib/network/=, =web/src/lib/components/=). The AI assistant's
  =fetch_from_relays= tool gates through the same Confirm flow.

* The intent pattern (the app's Confirm-mode surface)
The unit the UI approves is an *intent*: a user-initiated action emits a
structured "here is what I'll fetch and from where" *before* touching the
network; Confirm mode gates on it, Auto passes it through as an informational
toast. One shape, several callers — this is the place to track them:
- *Fetch intent* (=FetchEvent::Intent=, =begin_operation_with_summary=): a REQ.
  Carries the proposed relay set + a =RequestSummary= (filters / composition /
  DSL sentence). =FetchConfirmModal= renders it; the user drops/adds relays and
  =ConfirmDecision.relays= overrides the set the engine uses. Since
  2026-11-09 that choice is *session state* (off / on relays, applied in
  Auto too) — see
  [[file:decision-session-relay-choices.org][session relay choices]] —
  and the proposed set is read ∪ matching search relays ∪ hints
  ([[file:decision-relay-flags-search-kinds.org][one relay list, five flags]]).
- *Publish intent* (=FetchEvent::PublishIntent=): the broadcast counterpart —
  carries the event ids + destination relays so the UI correlates per-relay
  Accepted / Rejected.
- Nostrdown =embed= / =quote= / =slot= entity fetches ride the *fetch* intent
  (=FetchAlways= → Confirm), which is why a not-local reference's relay pull
  surfaces here — see [[file:feat-nostrdown.org][nostrdown]].

* Local-first and reactive (2026-11-09)
Views render from the local store and re-read when the engine announces an
ingest — =FetchEvent::Ingested { kinds, count, profiles }= on the fetch-events
stream, emitted from the one ingest funnel (=Engine::note_ingest_batch=). Web:
=$lib/network/ingest.ts=. The feed, the timeline picker, the bookshelf and the
profile cache subscribe; the feed keeps its rows up (dimmed) while a read is
pending instead of blanking.

The rule that goes with it: relay-bound work that fires on its own must not
hold its HTTP request open. A browser has about six connections per origin and
tendrl keeps two for SSE (fetch-events, signer channel), so a few requests
waiting on slow relays queue every local read behind them — a 10 ms nostrdb
read then looks like "Loading publications…" for seconds.
- [X] =POST /profiles/fetch= (background prefetch) detaches; profiles arrive
  through the announcement
- [ ] feed sync, bookshelf sync, discussions list/counts, wiki resolve,
  pull-user-data still hold their request (user-initiated, so one at a time)
- [ ] not yet measured in a real browser session — the connection-limit cause
  is inferred from timings (engine 10–35 ms, headless 54 ms), not observed

Open refinements:
- [[file:idea-entity-hinted-relay-intent.org][Entity-hinted relays in the intent]]
  — a =naddr= / =nevent= carries relay hints in its NIP-19 TLV; surface them in
  the modal *distinctly* (grouped/highlighted as "this reference points here") and
  offer a hinted-relay(s)-vs-full-set choice.

* The fetch contract: attributable, observable, interruptible (2026-08-11)

Every relay fetch now keeps three properties, enforced at the single choke
point all fetches pass through (=Engine::tracked_fetch_with_options=):

- *Attributable* — =FetchRecord.reason= carries the human cause ("Resolving
  references", "Search", "Profile lookup", …). Mechanism: a tokio task-local
  (=network::with_fetch_reason=) scoped by ONE axum layer mapping request
  path → reason (=server.rs::fetch_reason_for_path=) — no per-handler
  plumbing; the innermost scope wins, so a handler can override. Detached
  tasks attribute at their spawn site (the 60s section-sync loop does).
  =FetchTrigger= stays the *mechanism* axis; =reason= is the *why* axis.
- *Observable* — =NetworkStatus.active= lists in-flight fetches (id, relay,
  reason, started_at) alongside the =recent= ring buffer. Web: the modeline
  network pill (dim idle / green pulsing + count while pulling, polls
  =/network/status=) opens the *activity center* popover — active rows and
  a recent log where a per-row ▸ expands cause + exact query + error. This
  covers the fetches the intent/toast flow never sees (auto-mode backfills,
  LocalFirst misses, background sync).
- *Interruptible* — every fetch's guard registers a =CancellationToken=;
  the choke point =select!=s relay work against it. =POST
  /network/fetch-kill= ={id?}= kills one or all: socket work drops
  immediately, a ="killed"= FetchRecord lands, and the owning request
  continues with local results (kill ≠ error). Activity-center rows get ×;
  header gets "kill all". Known v1 limit: per-fetch semantics — a
  multi-chunk resolve starts its next chunk after a kill; propagating
  cancellation to the owning *operation* is the refinement.

Related idiom that landed with it: *consent once per screen* — the modeline
wiki-resolution pill sends the whole screen's unresolved topics through one
=mode_confirm= resolve → a single Confirm intent, instead of per-link
approvals. Generalizable to any bulk enrichment (embeds, discussions).
Any future fetch path (new transport, new caller) must preserve all three
properties — route it through the choke point or replicate them.

* NIP-42 on the fetch contract (2026-09-15)
Every socket (=relay::RelayConn=) runs the AUTH state machine; the choke
point above is unchanged, so attribution / observability / kill-switch all
still hold. Two new per-relay statuses on the =fetch-events= stream:
=auth_required= (relay wanted auth, tendrl did not authenticate — not opted
in, no signer, or refused) and =authenticated=. =FetchRecord.authenticated=
marks the activity log. Both are passive; the Confirm-mode intent approval
already covers AUTH for opted-in relays, no second modal.

* Gaps / open edges
- No per-source or per-kind fetch policies — the mode is engine-global.
- Performance (2026-08-12 audit): every relay fetch is a fresh
  WebSocket and +multi-relay read fanout is serial+ —
  [[file:fix-relay-connection-churn.org][fix-relay-connection-churn]]
  (read fanout made bounded-concurrent 2026-08-12, =READ_FANOUT = 8=,
  same guard/kill-switch semantics; connection reuse and the
  persistent layer remain open).
