#+TYPE: fix
#+STATUS: fixed

* The issue (observed 2026-08-12, v0.8.2)

=POST /nostrdown/resolve= is a serial per-item loop (=api.rs:864=), and
each item pays for the whole publication again:

1. Full depth-4 tree load, *unconditionally* (=publication.rs:2134=) —
   even when the item's refs never consult siblings (the
   =needs_siblings= gate at =:2145= guards only step 2).
2. =load_sibling_index= then *re-queries every node the tree load just
   fetched*, one =load_event_by_addr= at a time
   (=publication.rs:2408-2416=), discarding the already-loaded events.
3. Per-ref entity lookups run serially inside the ref loop
   (=publication.rs:2244=, =:2262=, =:2298=, =:2313=, =:2331=).
4. Misses are never memoized: under =local_first=, every
   permanently-missing sibling re-triggers the serial fresh-socket relay
   fanout *per item, per pass* — the exact shape the 2026-08-11 wiki
   batching fixed for topics (=publication.rs:2280-2286=), retained on
   the sibling half. Wiki batching itself is per-item, not per-request.

For M items over a publication of T tree nodes: ≈ M×(2T+E) locked
nostrdb queries + M×(missing×R) serial relay REQs. The reader sends
M = every loaded section, so a 60-section publication ≈ 7,300 locked
queries per pass — reproducing data the SSE stream just delivered.

Client side: the session cache is keyed by *content string*
(=api.ts:362=) so nothing can be warmed by coordinate before content
exists, and draft items are excluded entirely (=api.ts:361=) — the
composer preview runs a cold, relay-reaching, full-document resolve on
every effect run (see [[file:fix-reader-effect-churn.org][effect churn]]
for the 2 s trigger).

This is the structural reason *prefetching multiplies resolve cost
instead of amortizing it*: prefetch grows both M and T.

* Proposed fix (tactical — the handler keeps its shape)

- [X] One tree + sibling-index load per publication *per request*,
  shared across items — =resolve_refs_batch= (the handler now makes one
  call for the whole request; =resolve_refs_with_options= is a one-item
  wrapper). Better than spec'd: the depth-4 tree loads only when some
  item in the group actually *needs* siblings — entity-only items no
  longer trigger it at all (the old load was unconditional). The
  orphan-item containing-publication derivation also batches into one
  reverse a-tag lookup.
- [X] Build the sibling index from the =Publication='s already-loaded
  events; delete the re-query loop — =collect_sibling_entries= (pure);
  =load_sibling_index= and its helper =load_event_by_addr= deleted
- [X] Negative-result memo with TTL (mirror =unreachable_sections=) —
  =Engine.wiki_topic_misses=, 30-min TTL, recorded only after a pass
  that actually reached relays, cleared on relay add/reset, bypassed by
  =mode_confirm= ("resolve everything"); the local pass always runs so
  a topic ingested since the miss resolves immediately
- [X] Flush deferred wiki topics once per request, not per item —
  request-scoped deferral, grouped per preferred author (author drives
  candidate ranking; items of one publication share theirs)
- [X] Client: address-keyed cache entries; cache drafts with
  invalidation on edit instead of opting out — key =
  publication|author|coord|fp(content)|fp(siblings)= (compact ~64-bit
  fingerprints instead of the full content string); an edit changes the
  fingerprint so stale entries age out of the LRU. Correction to the
  issue text: =ndResolveCache= was already module-global in =api.ts=
  (not component state) — the fix was the key shape, not a hoist.

Absorbed without component edits: =SectionCard='s per-card resolve
(paginated/outline views POST per visible card) now hits the shared
tree/sibling context server-side and the reworked cache client-side.

The structural half — making resolution part of the stream so prefetch
≡ resolve — is [[file:fix-resolve-in-stream.org][its own zettel]].
