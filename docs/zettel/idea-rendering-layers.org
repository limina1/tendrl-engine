#+TITLE: Rendering layers — opt-in bases, grammars and block renderers over source text
#+TYPE: idea
#+STATUS: plan
#+DATE: 2026-10-01

The reader shows every section as one =pre-wrap= run of the stored text
with two engine-resolved overlays merged onto it (NIP-84 highlights,
nostrdown refs). A *rendering layer* is something the reader puts over
that text. The three markup bases are on by default since milestone 2
([[file:decision-layers-default-on.org][decision]]); a section that
declares no format still reads exactly as stored unless the user answers.

Branch: =feat/rendering-layers= (milestone 1 shipped 2026-10-01,
milestone 2 — Org + AsciiDoc bases, default-on — 2026-11-02).

* The model

Three granularities, each preserving more of the source than the next:

1. *Span decoration* ("decorated source") — the text stays byte-identical;
   a base contributes style spans over UTF-16 offsets (headings, emphasis,
   fences, links, dimmed sigils). This is org-mode's and CodeMirror's
   model, and the default reading mode when a base is active. Highlights
   and nostrdown keep their 1:1 DOM-offset ↔ content mapping for free.
2. *Block replacement* — a fenced block with an info string is replaced
   by a figure (Graphviz, Mermaid, PlantUML…), with a toggle back to
   source. Text outside the fence keeps its offsets; a highlight inside
   forces that block back to source. The babel source-block model.
3. *Whole-section rendering* — the base replaces the text with HTML.
   Needs placeholder substitution for nostrdown tokens and quote
   re-anchoring for highlights, and highlight *capture* must be disabled
   there (a NIP-84 quote taken from rendered text would not anchor back
   to the source for any client). Last, opt-in, read-only.

Layer kinds in the registry (=web/src/lib/layers/registry.ts=): =base=
(keyed by mimetype), =grammar= (code-fence syntax colouring, keyed by info
string), =block= (fence → figure). Milestone 1 ships =base= only; the
other two slot in beside =BaseImpl=.

* Precedence — tag or user, never heuristics

Which base renders a section (=layers/resolve.ts=):

1. =?highlight=<id>= deep link → source, forced (the anchor must land).
2. The per-buffer pick (T → render chips; =null= = source). Explicit beats
   remembered.
3. "Always for this book" binding (30040 coordinate).
4. "Always for <mimetype>" binding, keyed by the section's *effective
   format* — its own =m= tag, else the format its kind fixes by spec
   (30023 Markdown, 30818 AsciiDoc), else the one inherited from the
   nearest enclosing index that declares one, resolved engine-side
   ([[file:decision-mimetype-tag.org][decision]],
   [[file:decision-layers-default-on.org][kind formats]]).
5. The first *enabled* base registered for that format.
6. The user's *untagged* fallback (Settings → Layers), when the section
   declares nothing: steps 4–5 run with that format.
7. Source.

Disabled layers never resolve, so the Settings → Layers toggle is the
single switch. A binding value of =source= means "never decorate this".
Bindings and the enabled set live in =tendrl.layers= (localStorage,
per-device, never an event); the un-promoted pick lives in the buffer's
view state and dies with it. Syncing bindings via a kind-30078 settings
event would be a deliberate opt-in under the publishing philosophy.

* Execution tiers (where a renderer runs)

| Tier | Examples | Desktop | Android | Emacs |
|------+----------+---------+---------+-------|
| In-browser JS / WASM | =@lezer/markdown=, uniorg, asciidoctor.js, mermaid, Graphviz via =@viz-js/viz=, pikchr | yes | yes (WebView runs WASM) | n/a |
| Engine-side local tool | =dot=, =plantuml.jar=, ditaa, LaTeX | if installed | no | via the engine |
| Remote render server | Kroki, a PlantUML server | Confirm-gated | Confirm-gated | Confirm-gated |

Plus the fourth option that makes mobile robust: *render at publish time*.
The author's desktop has the tools; tendrl renders every diagram block
when a kasten is built or a section is published, publishes the SVG as an
addressable artifact (Blossom blob / file-metadata event) and tags the
fence with its reference. A phone, a reader without PlantUML, and every
other NKBIP client get the picture with no toolchain; a reader with the
tool can re-render. The diagram becomes a citable thing — the
reference-manager answer, and an AsciiDoc =image::= macro pointing at the
blob is universal across clients.

Install tiers: bundled lazy chunks (the Markdown base today — fetched
only once enabled and needed; keep the Android build slim); downloadable
packs (zip of ES modules + WASM with a pinned hash into
=<data_dir>/layers/<id>/=, Confirm-gated, served by the engine — works
on Android because the engine runs in-process there; a pack index can be
a Nostr event with a Blossom blob, as zapstore already distributes the
app); native tools detected, never installed.

* Security constraints

- Untrusted relay content runs these renderers. Mermaid has had XSS bugs:
  strict security level + sanitized SVG. PlantUML's =!include= reads
  local files: sandbox profile. WASM renderers are the safest tier.
- Rendered Markdown would carry image URLs; fetching them leaks the
  reader's address to arbitrary hosts, against the spirit of Confirm
  mode. Remote images stay placeholders until approved or a per-relay
  trust setting allows them.
- Nothing renders unless opted in; deep links force the text-preserving
  mode.
