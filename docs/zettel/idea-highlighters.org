#+TITLE: Idea: highlighters — highlight styles (label + colour)
#+TYPE: idea
#+STATUS: design — model settled 2026-11-11 (style lives on the highlight; set discovered from existing 9802s); prototype next
#+DATE: 2026-11-11

* What it means

A highlight today (kind 9802) carries the text, context, an optional
note and its source — no /function/, and its colour is only the
yours/theirs theme tint. A *highlighter* is a highlight style: a label
paired with a colour — =vocabulary=, =for=, =against=, =reference=, or anything the
reader names. Highlighting with one marks /what the passage is/, and the
reader paints it in that colour.

* The style lives on the highlight

No separate definition event. Each 9802 carries its own label + colour:

#+begin_src
kind 9802
["highlighter", "against", "#ff6b6b"]
#+end_src

The set of highlighters is *discovered from existing events*: the
distinct label → colour pairs found on 9802s. Consequences:
- "everything highlighted /against/" is a tag query over 9802s;
- a highlight is self-describing — any reader can paint it without
  fetching anything else;
- when one author used a label with several colours, the newest 9802's
  colour wins for that author's set.

* The picker

Shown when capturing a highlight:
- *Your highlights* — the label/colour pairs found on your own 9802s,
  plus *new* inline: a label, then a colour.
- *Use another's* — a separate button: enter an npub, and the picker
  offers the pairs found on that reader's 9802s (local first; a relay
  round for their 9802s is Confirm-gated like any user fetch). Picking
  one stamps the same label + colour on your highlight.
- Plain highlights (no highlighter) keep working as today.

* Colour

- *Standard*: a dropdown of the standard highlighter colours (yellow,
  green, blue, pink, orange, purple …).
- *Custom*: a button beside the dropdown pops up an HSV colour picker.
- A user can change the color of an existing highlight by clicking on the highlight, which brings up the "Highlights" modal/drawer, flashes the specific highlight, and the user can click that to change the color like they'd make initially, but it republishes a highlight with the appropriate tag information, and the old highlight is no longer displayed

- Default for a new label with no pick: a stable colour from the label
  hash.

* Engine / web split

- Engine: parse the =highlighter= tag (=discussions.rs= highlight parse);
  highlight resolution (=POST /api/v1/highlights/resolve=) carries label +
  colour onto each span; a "highlighters of <pubkey>" listing = distinct
  pairs over that author's 9802s (newest wins); publish stamps the tag.
- Web: the picker (yours / use another's / new), the colour dropdown +
  HSV popover, overlay paints spans in the highlight's colour, the
  highlights drawer filters by label.

* Decisions (2026-11-11)

- *Recolour* publishes a new 9802 carrying a supersede pointer
  (=["e", <old-id>, "", "supersedes"]=); the engine drops superseded
  highlights, so the old one leaves the list and the reader. Only your
  own highlights can be recoloured — on someone else's, the click offers
  "highlight with this style".
- *Overlap*: highlight display settings carry one alpha level for all
  highlights, so overlapping highlights stay legible; one =highlighter=
  tag per highlight (overlap comes from separate highlights).
- *Behaviour* is opt-in: the highlight modal has an "annotation" button
  that pulls in the annotation functionality for that highlight (e.g.
  =vocabulary= → a vocabulary ask, =for= / =against= → a pro/con view);
  without it, every label is plain.
- *No NIP-32 label* — the =highlighter= tag is enough.
