#+TITLE: Mobile & Android
#+TYPE: feature
#+STATUS: partial
#+DATE: 2026-07-28

The full integration plan from the shipped mobile shell to a signed,
distributable Android app. One track, three phases: finish the mobile
shell in the SPA (phone-browser testable), wrap engine + SPA in a Tauri 2
Android host, then make it feel native. Working branch: =feat/mobile-shell=.

* Orientation & decisions

The engine-owns-data architecture is the whole bet here: Rust owns
fetching/storage/derivation behind HTTP+SSE, the SPA is a static client,
so an Android app is the *same engine and the same SPA* in a different
container — not a port.

Decisions made (2026-07-27/28):

- *Path*: mobile shell inside the existing SPA first, Tauri 2 Android
  wrapper second. The engine links into the app process as a library
  (Android forbids shipping a separate server binary) and serves the
  embedded SPA to the system WebView over =127.0.0.1=.
- *Rejected: pure-browser build* (IndexedDB/WASM). nostrdb is an mmap'd
  LMDB C database; wasm32 has neither. A browser port means rewriting the
  data layer — a second engine, not a port. Revisit only if a
  WASM-viable nostrdb backend ever exists.
- *Shell split, not component split*: one SPA, two shells over the same
  =BufferStore=. Desktop keeps the WM (slots/splits/modeline/leader);
  mobile renders the three class slots as full-screen panels behind a
  bottom bar. Buffer components are shared unmodified — that is the
  parity mechanism, there is no second UI to keep in sync.
- *One launcher*: the M-x minibuffer (as a bottom sheet) is the single
  command/open surface on mobile; the work-buffer drawer is the single
  switcher (Amethyst's drawer pattern, =reference/amethyst=
  =DrawerContent.kt=).

* Phase A — finish the mobile shell in the SPA

Everything here is testable in a phone browser against the desktop
engine over LAN (milestone M0, below). Ordered; A1–A3 gate the merge to
=tendrl-web=.

- [X] *A1. Back-button / history integration.* Shipped 2026-07-30 as
  =web/src/lib/wm/mobile-nav.svelte.ts=: SvelteKit shallow routing
  (=pushState=/=replaceState= + reactive =page.state=), one entry per
  panel/buffer navigation via a central =$effect= watcher in
  MobileShell, a prioritized overlay-closer chain registered from
  =+page.svelte= (drawer → text-prompt → minibuffer → leader → modals →
  help sheets; NetworkModeChoice + confirm intents excluded by design),
  and a *guard entry* beneath the baseline so Back-at-root can consume
  an open overlay or deliberately exit. Hard-won timing subtleties (all
  CDP-verified): kit's router rejects history writes on the first mount
  tick, so the baseline write is always deferred one macrotask; a
  =writing= flag hides our own writes from the history watcher (kit can
  flush effects synchronously mid-write); entries carry a per-load
  session id so stale same-URL entries from previous loads are absorbed
  rather than misread as echoes. Desktop stays history-free.
- [X] *A2. Cross-class open semantics.* Came free with A1's central
  watcher: every =store.openBuffer= path (feed rows, profile, search,
  discussion refs) coalesces into one history entry per navigation —
  verified renderer-open → Back → feed restore via CDP.
- [X] *A3. Per-shell command visibility.* =Command.shells?=, four WM
  commands marked desktop-only, =mxEntries= filter + =executeCommand=
  guard (leader/binding side door toasts), "desktop-only" badges in the
  Settings command registry.
- [X] *A4. Buffer-internals mobile pass* (open-ended tail; prioritize
  from real phone use after merge):
  - [X] composer: action-bar wrap at narrow widths (Cancel no longer
    clips at 390px; =@media ≤600px= in ComposeView)
  - [X] composer: keyboard avoidance — two layers: the viewport meta
    gains =interactive-widget=resizes-content= (Android Chrome/WebView:
    layout viewport shrinks with the keyboard, so the flex shell +
    pinned compose actions just work), plus =shell.keyboardInset=
    (visualViewport tracking) → =--kb-inset= on =.page= for iOS-style
    browsers where the layout viewport stays full-height. The two never
    double-compensate (inset reads 0 where the meta applies). CSS
    wiring CDP-verified (=--kb-inset: 300px= → page 844→544, bar
    lifted); real-keyboard behavior needs the phone.
  - [X] reader: typography pass (=.section-content= steps --t-xs →
    --t-base with 1.65 leading ≤768px; continuous view padding +
    heading bumps; toolbar wraps) and a mobile TOC drawer — =§ toc=
    button in paginated/continuous + edge-swipe right to open / swipe
    left to close; rows reuse =outlineVisible=/=outlineExpanded= (same
    collapse state as outline view); jump keeps the view mode
    (continuous scrolls in place via ContinuousView's exported
    =scrollToSection=, paginated navigates). Registered as mobileNav
    closers (toc 58, highlights drawer 57) so Back consumes them —
    teardown re-registers dead closers (no stale closure after
    unmount). CDP-verified incl. Back-consume chain and touch swipes.
  - [X] modeline surfaces' mobile home: STATUS section pinned at the
    bottom of the work drawer — network row (dot + pill, tap toggles
    auto/confirm), relays (opens relay buffer), identity (connect /
    locked / @npub → connect flow, settings, or my profile), embedding
    counter. Pills are the same deriveds as the desktop modeline,
    prop-threaded from =+page= — one source. (The Confirm-mode fetch
    modal already renders fine on mobile.)
  - [X] toasts: bottom-center above the nav bar in the mobile shell
    (=toast-stack--mobile=; desktop stays lower-right)
  - [X] walkthrough/tours: =TourTip.mobile= per-shell overrides
    (anchor/body/placement), resolved in DiscoveryTip when the mobile
    shell is active — beats anchored to desktop chrome (sign-in,
    signed-in-noname, go-home, walk-done) retarget to mobile anchors
    (=mobile-menu= ☰, =mobile-bar=, =mobile-cmds=, =mobile-status=)
    instead of auto-skip-burning as seen. New
    =tendrl-run-walkthrough= palette command = the mobile home of the
    logo-W "First-run walkthrough" entry (works on desktop too).
    On-demand buffer tours (reader/composer/search W chips) already
    anchor inside buffer chrome and work unchanged; mode-line tours
    stay desktop-only by construction (their W chip lives on the
    mode-line). CDP-verified: sign-in surfaces its mobile body ringed
    to the cmds button.
- [ ] *A5. Touch highlight capture.* Selection handles → action popover

  reading app — worth its own design iteration on-device.
- [ ] Merge =feat/mobile-shell= → =tendrl-web= after A1–A3; A4/A5 land

* Phase B — Tauri 2 Android wrapper

The engine is already a library crate (=nostr_engine=); the Tauri host
depends on it, boots the axum server on a background thread bound to
=127.0.0.1:<ephemeral>=, and points the WebView at it. The SPA is
already embedded via rust-embed (release builds bake =web/build/= in),
so the WebView loads the same origin the desktop bundle serves — no
CORS, no IPC needed initially. Tauri buys packaging, the WebView bridge,
the hardware-back event, and later plugins (share intents, deep links).

- [X] *B1. Build spike* — DONE 2026-08-10 (host: =mobile/src-tauri=,
  app id =io.github.limina1.tendrl=; commands in =docs/commands.org=):
  - [X] toolchain: =cargo-ndk= + Android targets (=aarch64-linux-android=
    primary; =x86_64-linux-android= for emulator)
  - [X] cargo feature =embeddings= gating =fastembed= + =usearch= (off
    for Android initially — keeps ONNX Runtime out of the critical path;
    =~:= search degrades gracefully, engine already reports embedding
    status)
  - [X] compile the C/C++ deps under NDK: nostrdb (LMDB — expected fine;
    Damus ships it on iOS), secp256k1 (cc, well-trodden), =zip=/deflate
    (pure Rust, fine)
  - [X] =keyring= has no Android backend — feature-gate it; identity
    falls back to the existing ncryptsec-file + passphrase path
    (=identity.rs=), Android Keystore integration deferred
  - [X] gate =webbrowser= open-on-launch (desktop bundle behavior) off
    on mobile
  - [X] scaffold the Tauri 2 mobile project (proposal: =mobile/= dir,
    host crate depends on =nostr_engine= by path), WebView →
    =http://127.0.0.1:<port>/?shell=mobile=
  - [X] WebView cleartext: allow =127.0.0.1= via
    =usesCleartextTraffic= / network-security-config (localhost only)
  - [X] *loopback auth token* — Android loopback is device-shared: any
    app can reach =127.0.0.1:<port>=, and the engine currently treats
    "can reach me" as "is the user" (fine on desktop's single trust
    domain, wrong across Android's mutually-untrusted sandboxes). Host
    generates a per-boot secret, injects it into the WebView (initial
    query param; SPA sends it as a header on every request incl. SSE),
    engine middleware rejects requests without it. *Hard prerequisite
    for any signer on device* — otherwise a malicious app can drive
    =/identity/sign= and launder requests through tendrl's Amber
    grants (confused deputy). See
    [[file:../amber-nip55-signing-plan.md][Amber/NIP-55 plan]], security notes.
- [ ] *B2. Platform adaptation* (all small once B1 stands):
  - [X] data dir → app-private storage (Tauri path API → engine config;
    stable port 41347 so the WebView origin — and all SPA storage — survives
    restarts)
  - [ ] engine start/stop tied to app lifecycle; pause the 60s
    background fetch/embed loop and SSE on suspend, reconnect on resume
  - [ ] hardware back → =history.back()= (lands on A1's stack), exit at
    stack root
  - [X] config bootstrap: first-run TOML seed (=initial_relays=) written
    to app storage; =relays.json= as on desktop (localhost dev relay
    dropped from the defaults)
- [ ] *B3. Signing on Android.* No NIP-07 in a WebView. Ladder:
  - [X] *npub (watch-only) login* — the first page in, and currently
    the only mobile login: =IdentitySession.watch_pubkey= → state
    ="watching"= (=POST /identity/login-npub=); =by:me= / feed scoping /
    profile chip work via =effective_pubkey=, signing surfaces stay
    gated (=identityCanSign= is false). Settings lists the npub field
    *first*, before ncryptsec/NIP-07; a real key login displaces it.
    Secrets pasted into the npub field are rejected loudly.
  - [ ] engine signer (ncryptsec decrypt in-process — already
    supported; the right default for a single-user device app)
  - [X] *NIP-55 (Amber)* — shipped 2026-08-10, but NOT as an
    engine-side =Signer= impl: Amber registers as an *external signer*
    (kind ="nip55"=) over the existing SSE registry — the seam NIP-07
    built is already the intent bridge, transport-agnostically. WebView
    glue (=web/src/lib/identity/nip55.ts=) fulfils sign requests via the
    in-app Tauri Kotlin plugin (ContentResolver-first, intent fallback);
    the engine adds one enum variant + =verify_signed_event= (schnorr
    check on everything external signers return). Verified on device:
    connect, sign, publish. See
    [[file:../amber-nip55-signing-plan.md][the plan]].
  - [ ] NIP-46 remote signing as a third engine-side option
- [X] *B4. Debug APK on a real device* (milestone M1) — Pixel 7 over
  wireless adb, 2026-08-10: boot, token enforcement (outside process
  401s on =/api= incl. =/identity/sign=), feed sync (wss needed
  webpki-roots fallback — no OS cert store for rustls on Android),
  reading, Amber connect + signed highlight publish end-to-end.
  Still unverified: batch publish, deny path, silent restart
  re-attach, suspend/resume across the intent round-trip, first-contact
  approval vs the 60s timeout.

* Phase C — make it feel native

- [ ] *Share-intent import*: share a PDF/URL from any app → engine
  =document.rs= extraction → knowledgebase. The killer mobile feature
  for a reference manager; needs a Tauri intent handler + an import
  confirmation surface.
- [ ] Relay websocket reconnect discipline on flaky mobile networks
  (backoff + resume-on-foreground in =relay.rs= / fetch loop).
- [ ] Re-enable embeddings on mobile: ONNX Runtime Android build behind
  the =embeddings= feature; evaluate model size / battery; possibly
  on-demand ("embed while charging").
- [ ] Per-shell walkthroughs; mobile onboarding beats.
- [ ] Deep links: =nostr:= URI handler (naddr/nevent → reader buffer) —
  pairs with the deferred deep-link routing gap in
  [[file:feat-shell.org][WM shell]].

* Milestones & acceptance

- *M0 — phone browser over LAN* (available now on the branch): desktop
  engine running; phone on same network →
  =http://<desktop-ip>:5174/?shell=mobile= (or =:3030= for the embedded
  build). Accept: read a publication, run a search, switch panels,
  drawer + palette usable with touch.
- *M1 — debug APK*: engine boots in-process on device, fresh data dir,
  first-run flow completes, fetch/read/publish work on wifi + cellular.
- *M2 — daily driver*: A4/A5 landed; back button never accidentally
  exits; app survives background/foreground cycles without losing SSE
  or draft state; battery cost acceptable (no background polling).
- *M3 — signed release*: versioned with the existing release workflow
  (Cargo.toml version is the number; add =scripts/build-android.sh=
  alongside =build-portable.sh=; tag =v<version>=). Distribution:
  *zapstore* first (Nostr-native, Amethyst precedent), F-Droid later;
  Play Store not a requirement.

* Performance audit (2026-08-12)

The [[file:eval-performance-2026-08.org][August 2026 evaluation]] audited
the Android host. Corrections to this zettel's earlier assumptions:
embeddings are *on* for mobile (=embeddings-dynamic=, =lib.rs= enables
them unconditionally; the B1-era "off for Android" lines above are
historical), and the actual APK build is
=default-features=false, features=["embed-assets","embeddings-dynamic"]=
— not the =--no-default-features --features embed-assets= line
=docs/commands.org= keeps as a cross-compile check. Open issues:

- [[file:fix-android-boot-blocking.org][Boot blocking]] — engine boots
  via =block_on= on the UI thread, pre-WebView (ANR exposure)
- [[file:fix-android-lifecycle.org][Lifecycle gaps]] — suspend gates
  only the 60 s loop (the B2/M2 SSE half is still open); debug-level
  logcat in release
- [[file:fix-release-profile.org][Release profile]] — the 44 MB
  unstripped =.so=
- [[file:fix-relay-connection-churn.org][Relay connection churn]] — a
  radio wakeup per fetch; Phase C reconnect discipline is the fix's
  structural half
- The engine has zero =cfg(target_os = "android")= gates — the [[file:fix-ndb-lock-hold.org][query-lock]]
  and [[file:fix-background-tick-idle-cost.org][tick-cost]] issues hit
  hardest here (cold mmap faults from flash, battery)

* Verification

- Browser-side: the headless chromium + CDP pattern from
  =.claude/skills/verify= at 390×844 against an isolated worktree engine
  — used for everything shipped so far; keep driving each A-item that
  way before device testing.
- Device-side (M1+): =adb install= debug APKs; =adb logcat= filtered on
  the engine's tracing output; the engine's HTTP API remains fully
  scriptable on-device via =adb forward tcp:3030 tcp:<port>=.
