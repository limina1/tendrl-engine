* The issue (reported 2026-08-12, after the perf sweep)

The [[file:fix-resolve-cost-model.org][resolve batching]] made the wiki
lookup fast and one-shot — and thereby *silent*: the whole unresolved
topic set goes out as one request-scoped flush, so the modeline's
resolve counter sits still and then teleports (user report: "would jump
from 10 to 300, which in the middle time is just confusing if things
are hanging"). There is no intermediate signal between "sent" and
"landed"; on a slow relay the UI is indistinguishable from a hang.

This is a *feedback* gap, not a speed regression — the batch itself is
the right shape. Pre-sweep the counter advanced per item only because
the engine was doing M redundant flushes.

* Proposed fix (tactical)

- [X] +Chunk the client's relay backfill into bounded section groups+ —
  *shipped and reverted the same day.* On-device it multiplied relay
  cost instead of amortizing it: real articles repeat topics across
  sections, so consecutive chunks re-flushed the SAME topics before
  earlier fetches had ingested (device log: one identical 50-topic
  query sent 4× in 20 s against a ~5 s/query relay), and each chunk
  paid the slow relay's full wait. The backfill is ONE request again —
  the server dedupes topics request-wide, which was the point of the
  batching. What shipped instead for the wait itself:
  =find_wiki_events= now runs its 50-topic chunks *bounded-concurrent*
  (4 at once), so a 300-topic first pass costs one slow-relay wait, not
  six stacked. Stepwise counter movement belongs to
  [[file:fix-resolve-in-stream.org][resolve-in-stream]].
- [X] Busy-state messaging in the modeline tracker — the pill reads
  "N/M wiki · fetching…" while the pass is in flight (verified live via
  CDP: the counter advances chunk by chunk instead of teleporting).

*Regression caught during verification* (the reason to keep the CDP
fetch-count harness around): the first cut merged chunks with
=refsBySection = { ...refsBySection, ...m }= inside the effect's async
continuation — *reading* =$state= there re-enters tracking and
self-loops (the documented Svelte 5.53 query-flood family, previously
eliminated codebase-wide) — producing a 30-POST/s resolve storm that
Chrome's 5-minute intensive throttling masked into "stops on its own".
The shipped =apply= accumulates in a closure and stays *write-only* to
state. Rule reaffirmed: effect-spawned async callbacks must never read
reactive state.

* The structural cure

[[file:fix-resolve-in-stream.org][Resolve-in-stream]]: when resolution
rides the SSE tree stream, incremental progress falls out for free and
this zettel's chunking becomes unnecessary.
