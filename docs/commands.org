** Common error responses

- =400 {"error":{"message":"Invalid bech32 encoding: ...","type":"invalid_filter"}}= →
  the string is corrupted or has the wrong checksum (often a paste issue).
- =400 {"error":{"message":"Unknown HRP: foo","type":"invalid_filter"}}= →
  not a NIP-19 identifier we handle (only npub / nprofile / nevent / naddr).
- =400 {"error":{"message":"Missing required TLV type 0x00","type":"invalid_filter"}}= →
  payload structurally valid bech32 but missing a required field for the
  detected variant.

** Encoder symmetry note

The added =encodeNpub= uses =BECH32_CONST = 1=, not =BECH32M_CONST=
=0x2bc830a3=. NIP-19 splits the namespace: =npub= / =nsec= are
bech32, everything else (including =nevent= / =naddr= / =nprofile=)
is bech32m. =encodeNevent= correctly uses the bech32m constant. If a
copied =npub1...= fails to decode with the right pubkey, the
checksum constant is the first thing to suspect.

** Tag name shape

The parser accepts both single-char NIP-01 short tags ( =t=, =d=,
=e=, =a=, =p=, =L=, =m=, …) and multi-char names ( =author=,
=client=, =imeta=, =alt=, =subject=, =summary=, =published_at=, …)
as tag filters. =TagFilter.tag_name= is =String=.

Name shape constraint at =src/search.rs:506=: =[A-Za-z][A-Za-z0-9_]*=
plus a value that is non-empty and does not start with =/=. The
slash exclusion prevents URLs ( =https://example.com=) from being
misclassified as a tag filter ( =https= with value =//example.com=).

NB: =author:= is a TAG NAME — it filters events with an
=["author", "<val>"]= tag. It is NOT an alias for =by:=, which
filters by publishing pubkey ( =me= / =assistant= / =npub1...= /
=hex64=).

** Tag presence query

=has:NAME= matches any event with a tag whose first element is
=NAME=, regardless of the value. Useful when you don't know what
values to expect (e.g. =has:author= surfaces events that have any
=["author", ...]= tag at all).

Compose with other filters to make the initial fetch selective —
=k:30041 has:imeta= is much faster than =has:imeta= alone because
the kind filter narrows the DB-side fetch before the post-filter
runs.

#+begin_src bash
# Returns up to 500 candidate events, post-filtered to those with
# any "author" tag.
read -r -d '' Q <<'Q'
{"query":"has:author","policy":"local_only","scope_to_me":false}
Q
curl -X POST http://localhost:3030/api/v1/search \
  -H 'Content-Type: application/json' -d "$Q"
#+end_src

Implementation: =SearchQuery.has_tags: Vec<String>=, parsed in
=src/search.rs= (must be checked before the generic =name:value=
dispatch so =has:author= doesn't parse as =Tag("has", "author")=),
applied by =query::filter_by_has_tags= after the DB fetch.

** Tag value matching: substring + quoted phrases

For multi-char tag filters, the post-filter does *case-insensitive
substring* matching, not exact. =author:liminal= matches events
with author tags =liminal 🌑=, =Liminal Day=, =the liminal night=,
etc. This is the right default for display-name conventions where
emoji and casing vary.

Multi-word values via double quotes:

#+begin_src bash
read -r -d '' Q <<'Q'
{"query":"author:\"alice in wonderland\"","policy":"local_only","scope_to_me":false}
Q
curl -X POST http://localhost:3030/api/v1/search \
  -H 'Content-Type: application/json' -d "$Q"
#+end_src

Parser ordering note: the tag-prefix check at =src/search.rs:506=
runs BEFORE the quoted-Exact fallback. =author:"alice in wonderland"=
classifies as =TagFilter("author", "alice in wonderland")=, not as
an exact-text search. Plain quoted tokens with no recognized
prefix ( ="hello world"= ) still fall through to =TextFilter::Exact=
as before.

Single-char tag filters ( =t:= , =d:= , …) keep exact-match semantics
because they're applied at the nostrdb / NIP-01 layer where the
protocol mandates exact value match. Only the post-filter path is
substring-based.

** Tag-value histograms — =count:NAME=

=count:NAME= returns a histogram of distinct values for that tag
across the matched event set. Composes with other filters; the
aggregation runs AFTER all filtering, so the histogram reflects
exactly the events that would have come back as =results=.

Response shape:
=tag_counts: { NAME: [{value, count, event_ids: [...]}, ...] }=
sorted by count descending, ties broken alphabetically. Each
bucket carries the IDs of the events that contributed, so the UI
can render an unfoldable group view (header = value + count, fold
out = the actual events looked up in =results=). Empty when no
=count:= was requested ( =serde(skip_serializing_if)= keeps the
JSON clean).

#+begin_src bash
# All distinct author tag values across kind-30041 events,
# with how many events carry each + IDs of those events.
read -r -d '' Q <<'Q'
{"query":"k:30041 count:author","policy":"local_only","scope_to_me":false}
Q
curl -X POST http://localhost:3030/api/v1/search \
  -H 'Content-Type: application/json' -d "$Q" | jq '.tag_counts.author[:10]'
# →  [{"value":"liminal 🌑","count":42,"event_ids":["abc...","def...",...]},
#     {"value":"Claude","count":17,"event_ids":[...]}, ...]
#+end_src

Multiple =count:= clauses are independent buckets:

#+begin_src bash
read -r -d '' Q <<'Q'
{"query":"k:30041 count:author count:client","policy":"local_only","scope_to_me":false}
Q
curl -X POST http://localhost:3030/api/v1/search \
  -H 'Content-Type: application/json' -d "$Q" | jq '.tag_counts'
#+end_src

Counting is per-event (an event with two =["author","Claude"]= tags
adds 1, not 2 — same model as =Counter(set(...))= over each event's
tag set). Values are compared case-sensitively against the raw tag
value; if you want fuzzy aggregation, normalize client-side after
fetching.

* Phone-browser demo — SPA mobile shell over LAN (no APK)

phone's browser on the same Wi-Fi. Two things the normal run command
misses: bind =0.0.0.0= (the default is loopback — unreachable from the

[embedding]
enabled = false
[database]
data_dir = "/tmp/phone-demo-data"

./target/debug/tendrl-engine -c /tmp/phone-demo.toml \
  --host 0.0.0.0 --port 3131
#+end_src

Then on the phone: =http://<desktop-LAN-ip>:3131/= (=ip -4 addr= on the
desktop). The ≤768px viewport auto-selects the mobile shell; force it
either way with =?shell=mobile= (or =?shell=desktop=). Fresh engines

to auto first:

* Release → GitHub (full ship sequence)

Cargo.toml =[package] version= is the single source of the release
number; the =v<version>= tag is load-bearing (release-notes.sh anchors
the changelog range on the newest =v*= tag).

#+begin_src bash
# 1. Land the work on master, then bump + changelog + portable build (docker):
scripts/build-portable.sh --bump patch        # or minor|major|--version X.Y.Z

# 2. Review CHANGELOG.md + Cargo.toml diff, commit the release state:
git add Cargo.toml Cargo.lock CHANGELOG.md && git commit -m "v$(scripts/bump-version.sh)"

# 3. Publish to GitHub (tags HEAD if v<version> doesn't exist yet,
#    pushes the tag, creates the release: CHANGELOG section = notes,
#    target/portable/release/tendrl-engine-<version>.tar.gz = asset):
scripts/publish-release.sh --dry-run          # preview first
scripts/publish-release.sh

# 4. Push the branch too (the tag alone leaves the branch view behind):
git push origin master
#+end_src

Variants:

#+begin_src bash
scripts/publish-release.sh --no-asset         # notes-only release (no tarball)
scripts/publish-release.sh 0.8.1 --no-asset   # backfill an old, already-tagged version
gh release upload v0.8.2 <file> --clobber     # replace/add an asset on an existing release
#+end_src

Rebuilding the same version: =scripts/build-portable.sh= with no flags
(the changelog script refuses to stack a duplicate section, and
publish-release.sh refuses if the GitHub release already exists).
