* The rule

A clear separation of concerns, stated by the project owner and audited here:

- *RUST owns* — fetching, event storage/query, and ALL /algorithmic derivation of
  structured data from Nostr events/: parsing/classification, document-tree assembly +
  ordering, content-format detection, NIP-19 + NIP-11 decode/encode, kind-routing,
  event dedup/merge (replaceable-event latest-wins), slug / d-tag / coordinate
  generation, publish-payload emission, NIP-22 threading + NIP-84 highlight resolution,
  citation resolution, kind-0 author resolution.
- *TYPESCRIPT owns* — rendering, /ephemeral view & interaction state/ (focus,
  expansion/collapse set, scroll, selection, active view mode, panel widths), and
  calling Rust over HTTP/SSE.

Rationale: the algorithmic layer is pure (events in → structured data out), so it is
deterministic, testable once, and *portable to every frontend* (web, emacs, nvim, a
future TUI) without re-implementation or drift. View/interaction state is per-UI and
per-moment, so routing it through Rust over HTTP would be chatty and laggy — it stays
local to each frontend.

* Verdict

*Mostly compliant.* The boundary is already drawn correctly for the heavy lifting:
Rust assembles + orders + classifies; the web renders. Non-compliance is /contained/,
not pervasive:

- *No presentation leakage in Rust outside [[file:03-tree-module.org][src/tree/]].* engine/api/publication/query/
  relay/search deal only in events/filters/payloads. The view-state contagion is
  entirely inside the =src/tree= TUI state machine — which the web never consumes
  (=api.rs= imports only the compose payload structs from it).
- *A finite set of Type-A violations* — specific NIP transforms reimplemented in TS.
- *One structural lever* — the tree /stream/ ships flat nodes, forcing client
  reassembly even though Rust already has the assembled tree.

* Compliant — stays in TypeScript (do NOT over-correct)

These look like logic but are correctly frontend-local; moving them to Rust would be
the opposite mistake.

- [[web:src/lib/wm/renderers/ReaderBuffer.svelte::863][ReaderBuffer.svelte:863]] =walk()= — DFS *flatten of an already-assembled tree given an
  expansion depth*, with a defensive cycle guard. Rust already owns assembly+order
  (the stream delivers =children=/=is_root=/=is_index=). Flattening a known tree for
  display is the cheap view-layer transform. (Caveat: see the stream-shape fix — the
  cycle-guard + reassembly part is what should go, not the visibility flatten.)
- [[web:src/lib/search/search-config.svelte.ts::166][search-config.svelte.ts:166]] — regex *token-presence detection* to decide which
  config defaults to prepend; it never builds typed filters ([[src:src/search.rs::248][search.rs::parse]] does).
  UI-policy, not parsing. (Drift risk if =search.rs= adds operators — add a test.)
- [[web:src/lib/discussions/authors.svelte.ts][authors.svelte.ts]] — picks a display string (display_name→name→truncated pubkey)
  from an already-resolved cached profile. Pure view.
- [[web:src/lib/relay/nip11.ts][relay/nip11.ts]] — thin client; parsing is Rust ([[src:src/nip11.rs::286][nip11.rs:286]]) and consumed via
  [[src:src/api.rs::2090][GET /relay/info]]. (One latent dup: a local =normalizeRelayUrl= for cache keys —
  ideally key on the engine-returned canonical URL.)
- =fetch/relay-fetch.svelte.ts=, =network/fetch-events.svelte.ts= — fire fetches,
  render SSE intents/progress. No event merge/dedup/sort. Engine owns gating.
- The reference-pool membership/gc bookkeeping in =state.svelte.ts= (=held=/
  =in_context=/=in_compose=) — UI bookkeeping (the =dedupeLatestProfiles= part is the
  only algorithmic bit, flagged above).

to the web (see [[file:03-tree-module.org][03]]). So the resolution is *not* "move state to TS" (the web already
holds its own focus/expansion/scroll) — it is *drop the TUI view-state machine and
keep the pure core*. Enumerated view-state to drop (all in [[src:src/tree/state.rs][state.rs]] unless noted):

* The pure Rust core to KEEP / revive

Cleanly separable, already pure (verified — no =TreeState=/UI deps):
- [[src:src/tree/parser.rs][parser.rs]] (690 loc) — =ParsedDocument::parse(content, mode)= line classification.
  *Fully pure, not entangled.* This is the parser that should be the single source of
  truth (vs the TS compose parsing + the Python sidecar's classification step; note
  document /extraction/ — PDF/DOCX/EPUB bytes→text — legitimately stays Python).
- [[src:src/tree/content.rs][content.rs]] (216 loc) — =ContentDetector= format detection. Fully pure.
- [[src:src/tree/node.rs][node.rs]] (401 loc) — =TreeNode=/=NodeId= structure + accessors. Pure data.
- The /data/ fields of =ComposeState=/=SectionCompose=/=TagEntry=/=ComposeBlock= —
  already the only things =api.rs= imports; extract a pure =ComposeDraft= out from the
  editor view-state it's currently trapped with.
- =render.rs::visible_nodes= flatten *algorithm* — pure, but currently /entangled/: it
  reads =state.cursor=/=selected=/=expanded=/=is_reader_mode()=. To reuse it, refactor
  to =flatten(nodes, roots, expanded: HashSet, mode) -> Vec<FlatNode>= taking the
  expansion set as a parameter. (In practice the web reconstructs flatten from the
  ordered stream, so this is the lone "core" piece still coupled to droppable state.)

* Resolution order (cheap → real work)

1. *WIRE (trivial):* point the discussion badges at =discussions/counts=; stop the
   TS tally. ([[web:src/lib/wm/renderers/ReaderBuffer.svelte::164][ReaderBuffer:164]])
2. *REFINE (optional, not a bug):* the stream already ships structure (depth + ordered
   children). If you want assembly fully Rust-side, emit incremental /flattened ordered
   TOC rows/ so the reader drops its addr-keyed =StreamNode= reassembly and keeps only a
   render list + collapse state. Carries slug-on-section with it. Smaller than first
   stated — the assembly algorithm is already Rust's and wired.
3. *BUILD — NIP-22 threading* server-side; =discussions/list= returns the forest.
4. *BUILD — NIP-84 highlight resolution* server-side (also unblocks the offset-pinned
   highlights roadmap item).
5. *BUILD — NIP-19 encode endpoint*; delete the TS bech32m.
6. *BUILD — republish-diff* in Rust; delete TS =detectRepublish= + the slug mirror.
7. *DROP — the =src/tree= TUI view-state machine* (Type-B), keeping parser/content/node
   + the extracted =ComposeDraft= as the portable pure core. (This is the [[file:03-tree-module.org][03]] cull,
   reframed: keep the pure core, drop only the view-state.)

Step 1 is trivial; 3–6 close the NIP-transform gaps that would otherwise drift across
frontends (these are the real wins — genuinely-missing Rust logic); 2 and 7 are
cleanups. Note the publication-tree assembly — once thought to be the big lever — is
*already* Rust-side and wired; the duplication there is thin (status-tracking
re-accumulation), so it's demoted to an optional refinement.
