* What This Project Is

Tendrl is a local-first *reader, writer, and reference manager* built on the
Nostr protocol: read structured publications, research across a distributed
event network (structured search + semantic embeddings), compose and publish
NKBIP-01 publications, and manage references through the nostrdown reference
language. It treats Nostr events as a zettelkasten — atomic, tagged, addressable
notes that can be searched, discussed with an LLM, and assembled into
publications.

The system implements NKBIP-01, a convention for structured publications using
two Nostr event kinds:

- *kind 30040* — a publication index (table of contents, ordered list of
  section references)
- *kind 30041* — a section (an individual content block: a chapter, a code
  listing, a note)

A publication is an ordered assembly of sections. Sections are independently
addressable, versionable, and can appear in multiple publications. This is the
zettelkasten property: content is composed, not copied.

* Architecture

The system is two cooperating processes — the Rust engine (=src/=, port 3030)
and the SvelteKit web frontend (=web/=) — over an HTTP/SSE API:

** The governing rule — frontend/backend boundary
This split is what keeps the engine portable to any future frontend
without re-implementing logic per-frontend:

- *Rust owns* fetching, event storage/query, and *all algorithmic derivation of
  structured data from events* — parsing/classification, document-tree
  assembly + ordering, NIP-19/NIP-11 decode+encode, kind-routing, dedup/merge,
  slug/d-tag/coordinate generation, publish-payload emission, NIP-22 threading,
  NIP-84 highlight resolution, kind-0 author resolution.
- *TypeScript (=web/=) owns* rendering and *ephemeral view/interaction state*
  (focus, expansion, scroll, selection, active view mode), and calls Rust over
  HTTP/SSE.

When the same derivation appears in both, it is resolved toward Rust (wire the
Rust, delete the TS twin). The full rule lives in =CLAUDE.md=.

** Rust Backend
- *nostrdb* — embedded C database for Nostr events via Rust bindings. All
  queries start here; reads are serialized through a process-wide mutex.
- *Relay layer* — NIP-01 WebSocket client; fetches from multiple relays in
  parallel, deduplicates, ingests. Publishes signed events. Live runtime relay
  sets (=general= / =fetch= / =publish=) persist to =<data_dir>/relays.json=.
- *Engine* — query coordinator with three fetch policies (=LocalOnly= /
  =LocalFirst= (default) / =FetchAlways=) and a =NetworkMode= toggle:
  - =Auto= — relay fetches run automatically
  - =Confirm= — user-initiated fetches emit an intent the UI approves over SSE
- *Search* — structured query parser (tag, kind, author, text, NIP-19,
  semantic) compiling to NIP-01 filters with post-filter text matching.
  Semantic search via =~:concept= / =~:"phrase":k= over a usearch HNSW index.
- *Embeddings* — in-process ONNX (fastembed); model loads lazily, cached on
  disk, shipped beside the release binary. No external service.
- *Document extraction* — in-process (=src/document.rs=, pure-Rust crates) for
  PDF/DOCX/EPUB/HTML/TXT → ordered ={title, content}= pages.
- *Chat / LLM* — conversation state with a fragment model, context injection,
  edit mode. =LLMProvider= trait with Claude (Anthropic Messages API) and noop.
- *Publication builder* — constructs 30040/30041 event sets from compose state;
  handles block types (editable, imported reference, fork with lineage),
  republish-diff, and atomic output-kind-aware emission.
- *Identity / signing* — NIP-49 ncryptsec, OS keyring, pluggable =Signer= trait
  (engine in-process today; NIP-07 wired for web; NIP-46 typed, transport-less).

** Svelte Web Frontend
The primary UI is a SvelteKit 2 / Svelte 5 (runes) application built as a
*tiling-window-manager shell* — class-typed slots (=chat= / =work= / =research=),
stable-ID buffers, splits, a Doom-style leader popup, an M-x palette, and a
modeline, with vim-style modal navigation across every buffer. The full spec is
=docs/wm-shell.md=; the feature inventory is =docs/features.org=.

The earlier three-panel workbench and the per-route pages (=/p/=, =/compose=,
=/profile/=, =/ignored=) have been retired into buffer renderers.

** TUI (removed)
A ratatui terminal interface was the original frontend. It has been removed —
there is no =ratatui=/=crossterm= dependency and a single =[[bin]]=. Its
vim-flavored interaction model survives conceptually in the web shell's modal
navigation and keybindings; any future frontend will consume the same HTTP API.

* Key Design Decisions

** Unified Item Pool
The web frontend manages a single =ContextItem[]= pool. Each item has
=in_context= and =in_compose= flags routing it to the appropriate slot, with
held / in-context / in-compose states. Items are deduplicated by source event
identity (=source_event_id= / =source_addr=); editing in one place is visible in
the other. =◂= sends to context, =▸= publishes, search-Insert pushes to compose;
items with no flag are garbage-collected. Badge colors indicate sync state.

** Markup-Agnostic Compose
The composer does not impose a markup language. Full mode is structured section
cards; plain mode is a single CodeMirror 6 + vim buffer over a delimited
document (the heading delimiter is configurable — =#=, =*=, ===, or custom; tags
serialize as =:key: value=). Switching modes is lossless. Content itself can be
Markdown, Org-mode, AsciiDoc, or anything else.

** Chat as a Structured Buffer
The LLM conversation is a sequence of typed fragments (system, user, assistant),
each selectable, removable, and pushable to compose. Edit mode collapses the
whole conversation into one buffer with =---= delimiters and =[role]= headers,
freely editable; exiting re-parses back into typed fragments.

** Imported Content and Forking
A search result sent to compose arrives as a read-only (default-locked)
reference; the index carries an =a=-tag to the original — no new event is
created. To modify it the user forks: a new kind 30041 with a new =d=-tag, the
user's pubkey, and =a=/=e= "fork" lineage tags (NIP-54), content now editable.
This preserves attribution and keeps the derivation chain traceable.

** Publishing model
Drafts are unsigned (=DraftStore=). *Signing is the snapshot* — the only way
into the db; there is no passive unsigned-event path (=sign:false= is rejected),
and nostrdb keeps every signed version. Broadcast is a separate step that pushes
a signed snapshot to the publish relays. Relay-set edits are local-only state
and are never auto-published as kind 10002/30002 events.

** LLM Provider Abstraction
The chat backend is provider-agnostic: an async =LLMProvider= trait with
=ClaudeProvider= (Anthropic Messages API) and =NoopProvider= (testing). Context
notes are injected into the system message so the LLM sees them as reference.

* Status

The running system is in good shape: a complete Svelte 5 runes migration, a
coherent search parser, a working reference pool, consistent FetchPolicy /
Confirm-mode plumbing, and the WM/buffer shell as the only live frontend. The
mid-2026 boundary-compliance cleanup shed the dead TUI navigation tier, built
the four missing NIP transforms in Rust (NIP-19 encode, republish-diff, NIP-22
threading, NIP-84 highlight resolution) and deleted their TS twins, wired the
draft store, and dropped the former Python embedding/parse sidecar for
in-process ONNX + document extraction.

Live feature areas — search, compose, chat, feed/reader, publish/sign/broadcast,
identity, document import, embeddings, ignore list, profiles — are built and
exercised by the web UI (full inventory in =docs/features.org=).

** Open / in-flight work
